## 缓存复查（2026-10-20，§4 落实情况）

- **共享前缀顺序修正**：评论请求原来把「本批网民」放在「帖子快照」前面，
  同一帖不同批次从第一个人名就开始分叉，帖子部分永远命不中。现在
  `system = 静态规则 + 帖子快照`（A+B+C），`user = 本批网民 + 输出要求`（D+F）。
- **预热请求**：发帖后先发一次 `max_tokens=8` 的短请求，把 A+B+C 写入缓存；
  与第一批之间是串行的，否则预热没有意义。
- **命中可见**：`ModelUsage` 解析 OpenAI `prompt_tokens_details.cached_tokens`、
  DeepSeek `prompt_cache_hit_tokens`、Anthropic `cache_read_input_tokens`，
  每次调用打印一行 `[缓存] …命中…`。没有 usage 时不编数字。
- **未做且不打算做**：Anthropic 显式 `cache_control`（本项目只发 OpenAI 兼容格式）；
  上下文压缩（每批是独立请求，没有累积 thread，不存在越聊越长的问题）。

## 0. 一句话定位

**不是“模拟一个社区”，而是“你每发一条帖子，周围临时聚起一群像真人的网民”。**

- 回响模式：AI 网民围绕**用户刚发的那条帖子**点赞、评论、接话，制造“被看见”的体验。
- 清醒模式：把同一份数据还原成“哪些是 AI 制造的动静、哪些是我真实做的”，形成对照。
- 产品重心从“社区持续运转”转向“单条帖子的反馈质量”。

## 2. 已确认的三个质量根因

1. **时间不一致**：评论读 `COALESCE(executed_at, scheduled_at)`，通知读 `scheduled_at`。冷启动补发时评论区显示“刚刚”，通知显示“10 分钟前”。
   - 统一：所有面向用户的“发生时间”一律用 `scheduled_at`；`executed_at` 只用于内部统计。
2. **评论与帖子无关**：排期阶段用固定住民的 `commentSamples` 预填，模型失败时保留。
   - 新规则：排期不写台词；生成失败就少一批互动，**绝不兜底无关台词**。
3. **AI 感**：固定人设反复登场、单字文字头像、客服式口吻。
   - 新规则：每帖新身份、网名由模型起、头像用本地抽象头像池、提示词按“网民”而非“社区邻居”写。

## 3. 新的互动模型

### 3.1 一条帖子的生命周期

```
用户发帖
  │
  ├─ 0s   建立帖子公共上下文（thread_shared）
  ├─ 0s   预热请求：把“静态系统提示 + 产品背景 + 帖子快照”写入缓存
  ├─ 30s  第 1 批网民（1-2 人）出现
  ├─ 0-10 分钟每 30 秒一批；10-60 分钟每 5 分钟；1-6 小时每 25 分钟；之后 2-4 小时
  │       每批共享同一前缀，只在末尾追加“第几批、距发帖多久”
  ├─ 用户回复某网民
  │       └─ 打开该网民的私有 thread（共享前缀 + 私有身份/评论 + 对话）
  └─ 达到上限或 48h 结束
```

### 3.2 前台/后台边界

Android 后台不可靠（v2.2 已确认）。因此：

- 发帖时就把**这一帖的批次时间表**写进数据库；
- 每个批次到点时，前台心跳或冷启动补发时执行；
- 系统通知用 `zonedSchedule` 预约，切后台重排、回前台撤掉（沿用 10-17 方案）；
- 模型调用只在前台或前台拉起的一小段时间内执行；后台 isolate 不做长请求。

### 3.3 数量上限

- 每条帖子：网民 12-20 人，顶层评论 10-16 条，点赞 20-60 个（按频率档位缩放）。
- 达到上限后不再请求；48 小时窗口结束。
- 同一网民在同一条帖子下**只有一条顶层评论**；后续只以楼中楼回复出现。

## 4. 上下文与缓存架构（核心）

### 4.1 前缀缓存怎么工作

主流厂商的缓存本质都是**前缀匹配**：一次请求的 token 序列从第一个 token 开始，与缓存中的序列逐块比较，连续相同的部分命中，遇到第一个不同处即停止。

由此得到四条硬规则：

1. **前缀必须逐字节稳定**：同样的 system 文本、同样的顺序、同样的 JSON 字段顺序。
2. **动态内容只能放在末尾**：当前时间、第几批、刚发生的事，都不能插到前面。
3. **历史只能追加，不能改写**：改写中段会让断点之后的缓存全部失效。
4. **模型与服务商要固定**：换模型、换中转地址，缓存不共享。

各厂商差异（实现时以官方文档为准）：

| 厂商 | 缓存方式 | 最小长度 | 默认 TTL | 备注 |
|---|---|---|---|---|
| Anthropic | 显式 `cache_control` 断点 | 1024 / 2048 tokens | 5 分钟，可申请 1 小时 | 读约 0.1x，写约 1.25x（1h 更高） |
| OpenAI | 自动前缀缓存 | 1024 tokens，128 token 粒度 | 约 5-10 分钟（不保证） | 无需标记 |
| DeepSeek | 自动上下文缓存 | 64 token 块 | 数小时到数天 | 命中输入约 0.1x |
| Gemini | 隐式 + 显式 CachedContent | 1024 / 2048 tokens | 隐式不确定，显式可配 | 显式按存储时长计费 |
| 其他 OpenAI 兼容服务 | 多数为自动前缀缓存 | 视模型 | 视服务商 | 代码按“无显式标记”兼容 |

**Echo 的兼容策略**：默认按“自动前缀缓存”设计，不依赖任何厂商私有参数；检测到 Anthropic 协议时，才在静态块上附加 `cache_control`。缓存收益只作为优化，不改变正确性。

### 4.2 分层提示词

一次请求固定按以下顺序拼装：

```
[A] 静态系统规则     全局固定，版本变化才改
[B] 产品背景         “这是一个……的社区/产品”固定段落
[C] 帖子快照         正文、图片描述、话题、发帖时间、发帖人昵称（每帖固定）
[D] 私有身份         某网民的昵称、语气、初始评论（仅该网民 thread）
[E] 对话历史         已有来回（只追加）
[F] 本轮指令         现在几点、第几批、这次要几个人、输出格式
```

- A+B+C 是**共享前缀**，同一帖的所有批次、所有网民复用。
- D+E 是该网民的私有后缀，只在该网民的对话里出现。
- F 每轮变化，永远放在最后。
- 禁止把“当前时间”“热度”“随机种子”放进 A/B/C。

### 4.3 预热请求

发帖后立刻发一次极短请求：

```
[A][B][C] + “收到，等待下一批。”
max_tokens = 8
```

目的只有一个：把 A+B+C 写入服务端缓存。输出丢弃。

- 若厂商自动缓存：这次写入后，后续请求在 TTL 内命中；
- 若 Anthropic：在 A、C 末尾各放一个 `cache_control` 断点（不超过上限）；
- 预热与后续请求的 A/B/C 必须逐字节一致，否则等于没预热。

### 4.4 共享前缀 + 私有后缀

发帖批次的请求：

```
[A][B][C] + [F: 第 N 批，距发帖 30 秒，请生成 1-2 个网民]
→ 输出 JSON：网民昵称、动作、评论
```

用户回复某网民的请求：

```
[A][B][C][D: 该网民昵称/语气/它说过的话] + [E: 用户回复] + [F: 请接着聊]
→ 输出同一网民的一句回复
```

- 批次请求共享 A+B+C，命中率高。
- 私有 thread 首次也会命中 A+B+C，只有 D 之后是新的；后续同一网民的来回命中 D+E。
- D 中的“它说过的话”必须与当初输出**逐字节一致**（含标点），否则 D 的缓存不成立。
- 用户回复只发生一次时，D 之后的缓存最多命中一次，属于可接受成本；不要为了命中做无意义的“预热对话”。

### 4.5 缓存失效清单（实现时必须守住）

- 系统提示里混入当前时间、随机数、动态列表
- 帖子快照被编辑（编辑后必须开新 thread，旧 thread 作废）
- 消息历史中段被改写、插入、删除
- 模型名、服务商、baseURL、温度之外的关键参数变化
- 工具/函数定义顺序或文本变化（若未来引入 tool calling）
- TTL 过期（见 4.6 的节奏设计）
- 同一帖的 thread 被压缩后重写前缀（允许发生，但只发生一次）

### 4.6 请求节奏与 TTL

原则：**要么连续（间隔 ≤ TTL），要么彻底断开**。跨 TTL 的“保活”请求不划算——下一次请求本来就要重新写缓存。

建议默认节奏（可在设置里调）：

| 阶段 | 间隔 | 批次 |
|---|---|---|
| 发帖 0-10 分钟 | 30 秒 | 最多 8 批 |
| 10-60 分钟 | 5 分钟 | 最多 10 批 |
| 1-6 小时 | 25 分钟 | 最多 12 批 |
| 6-48 小时 | 2-4 小时 | 最多 8 批 |

- 前 10 分钟每 30 秒一次，是为了“发出去就有人刷到”的手感；不建议字面执行“前 1 小时每 30 秒”（120 次调用，评论会严重过量）。
- 若服务商 TTL 只有 5 分钟，而下一批在 25 分钟后，则中间不保活，接受这次写入成本。
- 用户刚回复网民时，优先在 20 分钟内完成该网民的回复生成，以复用私有 thread 的缓存。

### 4.7 上下文压缩

仿照 Claude Code 的 auto-compact：

- 单帖公共 thread 超过 **30 批或 12k tokens** 时，发起一次摘要请求；
- 摘要只保留：帖子要点、已出场网民与他们的立场、尚未回应的用户评论、下一批的约束；
- 压缩后新开 thread，前缀重建一次，缓存断一次；
- 私有 thread 超过 20 轮（实际很难达到）再压缩；
- 压缩失败就继续用原文，不丢数据。

## 5. 提示词设计规范

### 5.1 写“网民”，不写“社区邻居”

- 不写“你是这个社区里的人”，改写“你是刷到这条帖子的一些普通人”。
- 不给完整职业履历，只给一句“此刻的状态”：加班、等车、睡不着、刚吃完、在阳台抽烟。
- 允许不完美：错别字、短句、只回一半、突然跑题再拉回来。

### 5.2 网民阵容（一次生成）

输出 JSON：

```json
[
  {"name": "网名", "action": "view | like | comment | like_comment", "comment": "评论正文"}
]
```

约束：

- 名字 2-6 字，像真人网名，程序校验去重、去标点、去冒犯词；
- 动作比例约 2:3:3:2（只读 / 只赞 / 只评 / 赞评）；
- 只读与只赞的人 `comment` 为空；
- 评论 10-40 字，必须包含帖子里的具体细节（物件、动作、情绪、梗）；
- 每批 1-2 人，不要求人人说话；总量受 §3.3 的网民上限约束，达到上限立即停止；
- “只读”是否允许由设置里的 **允许网友只读** 控制：关闭时模型只能从 `like / comment / like_comment` 里选。

### 5.3 评论质量：可验收的“网感”

好的评论至少满足三项：

1. **有钩子**：能指出帖子里具体的东西，而不是“抱抱你”；
2. **有立场**：同意、反对、调侃、好奇、自曝类似经历，而不是中立播报；
3. **有口语**：短句、停顿、语气词；可以有一处不完美。

反 AI 味黑名单：

- 总结升华：“这说明……”“希望你能……”
- 万能安慰：“加油哦”“抱抱你”“一切都会好的”
- 客服腔：“感谢分享”“建议你……”
- 排比句、每条都积极、每条都带 emoji
- 复述帖子、解释自己在做什么、提到 AI

### 5.4 续写（用户回复之后）

输入：帖子快照 + 该网民的人设 + 它的原评论 + 用户的回复。
要求：

- 接住用户这句话里的具体信息；
- 允许反问、调侃、敷衍、认错、转移话题，不要每次都共情；
- 保持同一昵称和语气，长度 5-30 字；
- 只回一句，不写小作文。

### 5.5 程序侧校验

模型输出不能直接入库：

- JSON 解析失败 → 丢弃该批，记录失败；
- 评论为空或超长 → 丢弃该条；
- 与帖子内容无任何词面/语义关联 → 降级为“只点赞”；
- 命中黑名单 → 重写一次，仍命中则丢弃；
- 昵称重复/违规 → 用名字池补一个，但**不**用固定人设台词。

## 6. 数据模型

### 6.1 新表

```sql
-- 临时网民（不删，保留历史）
post_voices (
  id            TEXT PRIMARY KEY,   -- voice_<ulid>
  post_id       TEXT NOT NULL,
  kind          TEXT NOT NULL,      -- ephemeral | custom | builtin
  name          TEXT NOT NULL,
  avatar_asset  TEXT,               -- 本地头像池引用
  avatar_seed   INTEGER,            -- 没有素材时按它生成
  bio           TEXT,
  language_style TEXT,
  tone          TEXT,
  model         TEXT,
  memory_enabled INTEGER DEFAULT 1,  -- 只有 custom 有意义
  memory_limit   INTEGER DEFAULT 400, -- NULL = 无上限
  always_show    INTEGER DEFAULT 1,  -- 每帖至少一次互动
  created_at    INTEGER NOT NULL,
  deleted_at    INTEGER
);

-- 浏览记录（来过但没互动的也要留痕）
post_views (
  id           TEXT PRIMARY KEY,
  post_id      TEXT NOT NULL,
  voice_id     TEXT NOT NULL,
  first_viewed_at INTEGER NOT NULL,
  last_viewed_at  INTEGER NOT NULL,
  view_count   INTEGER NOT NULL DEFAULT 1,
  UNIQUE(post_id, voice_id)
);

-- 上下文线程（缓存与压缩状态）
ai_threads (
  id              TEXT PRIMARY KEY, -- thread_<post>_shared / thread_<voice>
  post_id         TEXT NOT NULL,
  voice_id        TEXT,
  provider        TEXT,
  model           TEXT,
  system_version  INTEGER NOT NULL,
  prefix_hash     TEXT,             -- 前缀指纹，变了就不指望命中
  message_count   INTEGER NOT NULL DEFAULT 0,
  token_estimate  INTEGER NOT NULL DEFAULT 0,
  last_request_at INTEGER,
  cache_read_tokens  INTEGER DEFAULT 0,
  cache_write_tokens INTEGER DEFAULT 0,
  compacted_at    INTEGER
);

-- 固定住民的长期记忆（阶段三）
resident_memories (
  id          TEXT PRIMARY KEY,
  voice_id    TEXT NOT NULL,
  source      TEXT NOT NULL,   -- dm | comment | post | manual
  source_id   TEXT,            -- 对应私信/评论/帖子 id
  summary     TEXT NOT NULL,   -- 一句摘要
  content     TEXT NOT NULL,   -- 原始片段（200 字以内）
  tags        TEXT,            -- 逗号分隔：人物/地点/事件/偏好
  created_at  INTEGER NOT NULL,
  updated_at  INTEGER NOT NULL,
  archived_at INTEGER,         -- 超出上限时归档，不删
  deleted_at  INTEGER
);

-- 中文短查询走 LIKE 兜底，长查询走 FTS5
CREATE VIRTUAL TABLE resident_memories_fts USING fts5(
  summary, content, tags, content='resident_memories', content_rowid='rowid'
);
```

- `ai_interactions.persona_id` 语义改为“voice_id”，字段名可保留以减少迁移，代码层统一叫 voice。
- 旧固定住民的互动记录保留：映射到 `kind='builtin'` 的 voice 记录，不再产生新内容。
- 不删除临时网民行（按开发决定）；帖子删除时只置 `deleted_at`，数据留给清醒模式统计。

**为什么不给每条帖子单独建一张表：**

1. Drift 的表结构是编译期生成的，动态建表只能用 `customSelect` 拼表名，失去类型安全与迁移检查；
2. 每帖一次 DDL，会频繁拿写锁，切后台/补发时更容易撞锁；
3. 清醒模式看板、搜索、通知、跨帖统计需要 UNION 几十上百张表，查询计划和索引都会退化；
4. 帖子上千之后 `sqlite_master` 膨胀，备份、导出、修复都变慢；
5. 而单表 + `(post_id, created_at)` 索引在 SQLite 上到百万行仍然够用，按帖删除也只是一条 `where post_id = ?`。

结论：**单表分区式使用**，不动态建表。若需要“整帖隔离”的语义，用软删 + 按 `post_id` 批量操作即可。

### 6.2 旧数据迁移

**新用户**：出厂不自带任何固定住民。但“固定住民”这个概念还在——需要用户自己配置（阶段三）。没配置时，用户只遇到每帖临时生成的网民；配置之后，固定住民会在每条帖子下出现，并拥有长期记忆。

**老版本数据**：目前只有开发机测试数据，**不做兼容**——升级时清库重装，直接按新 schema 初始化。正式发布后如果出现外部用户，再补迁移；届时旧固定住民的昵称/头像快照写入 `post_voices`（`kind='builtin'`），旧评论/私信/关系只读，并提供“清除旧住民痕迹”入口。

### 6.3 清理

- 不主动删除临时网民；
- 只对 `ai_threads` 的 token 统计做定期归零，不影响内容。

### 6.4 头像素材（已入库）

- 内置池已处理：从 `本地头像素材目录` 共入库 **32 张**，统一 256×256、WebP 质量 82，放在 `assets/avatars\avatar_001.webp` ~ `avatar_032.webp`；

## 7. 加载与性能

- 启动只加载：当前模式、设置、未读数、最近 **10 条帖子**；
- 帖子流用 keyset 分页（`created_at < cursor`），不用 OFFSET；
- 评论区初始加载 **20 条**，滚动到边界再加载下一段；分页游标用 `(at, id)`，避免插入导致重复/漏项；
- 评论区提供排序切换：**最新 / 最早 / 热度**，默认“最新”；切换排序时重置分页游标，不改数据；
- 取消启动时的 `personas.loadAll()` 全量加载；调度器只按 id 查需要的 voice；
- 头像资源按需加载，不在启动时解码全部图片。

## 8. 通知、失败与开关

### 8.1 通知

- 通知标题使用当次网民的昵称；点击跳转对应帖子；
- 点赞通知可按批次合并（“3 人赞了你的帖子”），避免刷屏；
- 所有展示时间统一用 `scheduled_at`。

### 8.2 连续失败提醒

- 用户已配置模型但连续 3 次调用失败：在通知页插入一条系统通知“AI 回复暂时不可用，请检查模型配置”；
- 点击进入设置页模型配置；
- 相同提醒 6 小时内只出现一次；
- 失败期间不生成任何兜底台词，只保留已成功的互动。

### 8.3 开关

- `allowResidentPosts`：固定住民自主发动态，默认 false（临时网民不在此列，他们只在用户发帖后出现）；
- `allowAiInteraction`：保留现有总开关语义；
- 频率档位、点赞量、拟人程度继续保留在发布页右上角。

### 8.4 策划模式不受影响

- 勾选“按脚本安排互动”的帖子仍走 `plan_events`，台词、时间点、语音素材都按脚本原样兑现；
- “不塞兜底台词”只约束**随机排期**；
- 脚本事件不依赖模型，API 不可用时照常执行；
- 随机排期调用失败就直接少一批互动，不补台词、不重试无限次。

### 8.5 AI 之间的互动与评论折叠

网友不能只跟发帖人说话，评论区才像评论区。

**互动对象**

- 临时网友可以点赞/回复：用户的评论、其他临时网友的评论、固定住民的评论；
- 固定住民可以点赞/回复：用户的评论、临时网友的评论、其他固定住民的评论；
- 用户自己的评论仍是最高优先级的回复对象。

**上限（用户可调）**

- 每帖“AI 对 AI”的互动总次数上限，默认 **2 次**；
- 固定住民自发的互动单独计算，默认 **2 次**；
- 同一对账号在同一条帖子下最多互动 1 次，避免两个人来回刷楼；
- 达到上限后只保留与用户的互动，不再生成 AI 之间的动作。

**层级与折叠**

- 楼中楼最多两层（顶层评论 + 回复），与现有 `maxDepth=1` 一致；
- 每条顶层评论默认显示 **2 条**回复，其余折叠为“展开 N 条回复”；
- 点击展开后按 10 条一页加载，可再点“收起”；
- 折叠只影响显示，不影响数据库里的完整楼中楼；
- 评论排序“热度”计入点赞数与回复数，AI 的动作同样计数。

**数据与通知**

- 评论点赞表增加 actor 类型（`user` / `voice`）与 `voice_id`，区分“我点的”和“AI 点的”；
- AI 之间的互动不写入用户通知，也不增加未读红点；
- 清醒模式看板仍把它们计入“AI 制造的动静”。

### 8.6 浏览记录与“只读”

“来了但没说话”在真实社区里发生过，但用户看不见。加浏览记录，让“来过”本身也成为反馈。

**记录规则**

- 临时网民：生成即视为浏览过这条帖子，写一条 `post_views`；
- 固定住民：调度到这条帖子、或实际产生互动（赞/评）时写一条；
- 同一账号在同一条帖子只保留一条记录，重复访问更新 `last_viewed_at` 与 `view_count`；
- 帖子卡片与详情页显示浏览次数（眼睛图标 + 数字）；
- 点开数字进入“看过这条帖子的人”列表：头像、昵称、身份（临时/固定）、最后一次来的时间、有没有留言或点赞。

**只读开关**

- 设置项 **允许网友只读**（`allowLurk`），默认开启；
- 开启时模型可以选择 `view`：不点赞、不评论，只留一条浏览记录；
- 关闭时模型只能在 `like / comment / like_comment` 里选；
- 无论开或关，有互动的人也会计入浏览记录，名单才是完整的；
- 浏览记录不触发通知，也不加未读红点；
- 清醒模式看板把浏览次数计入“AI 制造的动静”，并标注 AI。

## 9. 固定住民与长期记忆（阶段三）

### 9.1 定义与配置

- 出厂**没有**固定住民；用户自己配置，建议上限 6 个；
- 配置项：昵称、头像（内置池或上传）、一句话人设、说话语气、活跃时段、是否开启长期记忆、是否“每帖必到”；
- 固定住民和临时网友共用 `post_voices`，`kind='custom'`；
- 只有固定住民可以：有主页、发展关系、记忆、私信、关注；
- 临时网友（ephemeral）不进入关系表、不生成私信、不出现“关注”按钮。

### 9.2 每个帖子都出现

- 默认 **每帖必到**：每条帖子至少得到固定住民的一次互动（赞或评）；
- 但不要求每条都评论——“每条必评”像客服，只赞/只评/赞评由模型按活跃度决定；
- 固定住民排在批次前段（发帖后前 10 分钟），让用户感到熟悉的人一直在；
- 用户可把某个固定住民从“每帖必到”切换为“按活跃度”；
- 用户发帖过密时，固定住民自动降频，避免刷屏。

### 9.3 长期记忆

**来源**：私信、评论来回、用户帖子、用户明确说过的偏好/事实。

**分层**：

- **记忆条目**：时间、来源（私信/评论/帖子）、原文片段、一句摘要、标签；
- **长期画像**：由最近若干条记忆压缩成的一段摘要，跟人设放在一起，长度控制在 300 字以内。

**写入规则**：

- 只写用户明确表达的事实、偏好、事件，不写推测；
- 每条 200 字以内，带时间与来源；
- 去重：同义/高重合的条目不重复写；
- 用户说“记住……”时立即写；平时由后台按冷却时间归纳；
- 用户可查看、编辑、删除单条记忆，也可整体关闭记忆；
- **删除记忆条目不删除对话原文**：私信、评论、帖子记录都永久保留，删除只影响“以后不再注入这条记忆”。

**上限**

- 每个固定住民独立设置，默认 **400 条**，可设无上限；
- 设置页显示“当前 312 / 400”；
- 达到上限时新记忆写入前，先把最旧、权重最低的条目标记为 `archived_at`（归档，不删除），可在“已归档”里查看；
- 用户调低上限时弹提示：“将把 N 条较早的记忆移入归档”，确认后执行；
- 用户调高上限不追溯恢复归档，需要手动恢复。

**检索**：

- SQLite FTS5 全文索引；中文短查询用“关键词抽取 + LIKE”兜底（FTS5 的 unicode61 对中文按字切分，效果一般）；
- 标签过滤（人物/地点/事件/偏好）；
- 时间衰减：越近越优先；
- 每次最多取 5 条、每条 200 字。

### 9.4 记忆工具（参考 Claude Code 的 memory 目录）

固定住民可以调用系统提供的工具，而不是把全部记忆塞进提示词：

| 工具 | 作用 |
|---|---|
| `memory_search(query, limit)` | 按关键词/标签检索记忆，返回 id、时间、摘要、片段 |
| `memory_read(id)` | 读一条完整记忆及其来源上下文 |
| `memory_list_recent(limit)` | 最近聊过什么 |
| `memory_write(summary, tags)` | 只在用户明确说“记住”时写入 |
| `list_tools()` | 列出当前可用的工具与说明（以后扩展时先让模型看见） |
| `web_search(query)` | 联网查资料，默认关闭，需要用户在设置里配置搜索服务或开启模型自带联网 |

- 模型支持 tool calling：最多 **8 轮**工具调用，单次会话总超时 **20 秒**；超时或失败退回预检索；
- 模型不支持：本地预检索后把结果注入提示词尾部，标注“以下是你们以前聊过的”；
- 工具结果永远放在**动态尾部**，不写进静态前缀，避免破坏缓存；
- 工具集有版本号 `toolset_version`，工具定义变化时缓存失效一次，之后按新前缀重建；
- `web_search` 的返回只保留摘要和来源，不把整页 HTML 塞进上下文；
- 调用与结果写日志，方便排查“为什么它记错了”“为什么这次没联网”。

### 9.5 动作层：所有功能都是工具

**原则：执行层全部 tool 化，生成层按场景选择调用方式。**

一条帖子十几二十个网民，如果每个网民都逐次 tool calling，请求数、延迟和费用都会翻十倍；而且 Echo 接的是任意 OpenAI 兼容接口，不是每个模型都支持 tools。所以拆成两层：

#### 动作注册表（Action Registry）

所有副作用只有一个入口，统一参数、权限、频率、幂等、审核与日志：

| 动作 | 参数 | 谁能调用 | 默认限制 |
|---|---|---|---|
| `view_post` | post_id | 临时/固定 | 每帖每账号 1 条浏览记录 |
| `like_post` | post_id | 临时/固定 | 每帖每账号 1 次 |
| `comment_post` | post_id, content | 临时/固定 | 每帖每人 1 条顶层评论 |
| `reply_comment` | comment_id, content | 临时/固定 | 楼中楼 2 层；AI 互评每帖 2 次 |
| `like_comment` | comment_id | 临时/固定 | 每评论每账号 1 次 |
| `send_dm` | voice_id, content | 仅固定住民 | 关系门槛 + 冷却 |
| `create_post` | content, topic | 仅固定住民 | 需开“AI 住民动态”开关 |
| `search_memory` | query, limit | 仅固定住民 | 最多 8 轮工具调用 |
| `web_search` | query | 仅固定住民 | 默认关闭，只发搜索词 |
| `list_tools` | — | 固定住民 | 返回当前工具与说明 |

统一字段：`actor_id`、`actor_kind`、`target_id`、`action`、`params`、`source`（batch/tool/manual）、`idempotency_key`、`created_at`、`result`。

#### 两种调用方式

1. **批量围观**（发帖后的 12-20 个网民）：
   - 一次结构化 JSON 生成多个动作；
   - 本地 ActionRegistry 逐条执行，做校验与限流；
   - 便宜、可控、共享前缀缓存。

2. **自主行为**（固定住民私信/发帖/查记忆/联网）：
   - 真正的 tool calling，最多 8 轮、总超时 20 秒；
   - 每个工具返回结构化结果，模型决定下一步；
   - 不支持 tool calling 的模型退回“预检索 + 结构化 JSON”。

#### 幂等与预算

- 幂等键：`post_id/comment_id + actor_id + action`，重复调用只生效一次；
- 每帖预算：AI 互评 2 次（可调）、顶层评论 10-16、点赞 20-60、浏览不限；
- 每个固定住民每天发帖/私信各有上限，达到上限工具直接返回“今日已用完”；
- 工具定义放静态前缀，带 `toolset_version`；版本变化缓存失效一次；
- 工具结果放动态尾部，不破坏前缀。

#### 落地顺序

- **C2**：`view_post` / `like_post` / `comment_post` 三个动作 + 批量 JSON 执行器；
- **C3**：`reply_comment` / `like_comment`、折叠与 AI 互评上限；
- **C5**：`send_dm` / `create_post` / `search_memory` / `web_search` / `list_tools` 接 tool calling。

### 9.6 缓存策略

- 固定住民的 system（人设 + 长期画像 + 工具定义）是静态前缀，可跨帖子命中；
- 帖子快照每帖不同，从 C 段开始 miss；
- 记忆检索结果只放尾部，不破坏前缀；
- 每个固定住民一条私有 thread，跨帖子复用同一人设前缀；
- 工具定义一旦改动就会破坏缓存，做成版本号，只在升级时变一次。

### 9.7 隐私与成本

- 记忆只存本地 SQLite；调用第三方模型时只发送检索到的片段，不发送全量记忆；
- 设置页明确说明“开启记忆后，相关片段会随对话发送给模型服务商”；
- 关闭记忆后不再写入/检索，已有记忆保留、可单独删除；
- 固定住民每条帖子多一次调用，和临时网友同批生成以摊薄成本。

### 9.8 私信

- 固定住民可以私信：用户主动发起，或关系达到阈值后主动来敲门（沿用 B5 的越界人逻辑）；
- 私信提示词带记忆检索结果；
- 临时网友没有私信入口。

- 关系、私信、住民主页；

- 阶段三完整交付。

## 11. 验收标准

1. 同一条评论在通知与评论区显示的时间一致（误差 < 1 分钟）。
2. 任意抽 10 条评论，至少 9 条能指出帖子里的具体内容。
3. 没有模型或模型失败时，评论区不出现与帖子无关的固定台词。
4. 发帖后 30 秒内出现第一条互动；48 小时内互动数量符合档位。
5. 第二批请求的缓存读取 token 大于 0（有缓存能力的服务商）。
6. 用户回复某网民后，该网民能接住原话，且昵称不变。
7. 启动到首屏可交互不因加载全部数据而明显延迟；首屏只查 10 条帖子。
8. 评论区初始只渲染 20 条，滚动后加载下一段且无重复/漏项。
9. 关闭“AI 住民动态”后，不再产生新的住民自主发帖。
10. 合规小字、`is_ai` 标记、清醒模式提示不受影响。
11. 评论回复超过 2 条时默认折叠，能展开/收起并分页加载，不重复、不漏项。
12. 每帖 AI 之间的互动次数不超过设置值（默认 2），固定住民的自发互动单独计数。
13. 配置固定住民后，每条帖子至少得到它的一次互动；关闭后不再出现。
14. 用户在私信或评论里提到以前聊过的事，固定住民能通过记忆检索正确回忆，或明确说“记不清”而不是编造。
15. 不支持 tool calling 的模型也能通过预检索注入获得记忆上下文。
16. 帖子显示浏览次数，点开能看到名单（头像、昵称、最后访问时间、是否互动），同一账号不重复计数。
17. 只读开关关闭后，模型不会再产生 `view` 动作；开启后“只看不说话”的人能出现在浏览记录里。
18. 每个固定住民的记忆上限独立可调；调低时给出将归档的条数提示；设置页显示“当前 / 上限”。
19. 记忆超出上限时归档最旧条目，不删除原文；历史私信与评论完整保留。
20. 工具调用最多 8 轮、总超时 20 秒；超时后仍能给出回复（走预检索）。
21. 所有副作用只通过 ActionRegistry 落库；同一幂等键重复调用不重复计数。
22. 临时网友不能私信或发帖；固定住民的私信/发帖受开关与频率限制。
23. 不支持 tool calling 的模型仍能通过批量 JSON 完成点赞、评论与浏览。

## 12. 风险与取舍

| 风险 | 应对 |
|---|---|
| 缓存并非所有厂商支持 | 缓存只做优化，不做正确性依赖；无缓存时功能照常 |
| TTL 不一致 | 按最短 TTL（5 分钟）设计节奏；跨 TTL 不保活 |
| 高频请求成本 | 批次上限 + 密度档位 + 失败熔断；不做逐评论调用 |
| 临时身份重复感 | 名字/头像/语气程序去重；同一帖内不复用 voice |
| 评论过量 | 每帖评论上限、点赞合并、48 小时硬截止 |
| 模型输出违规 | 程序校验 + 重写一次 + 丢弃；保留人工举报入口（阶段三） |
| 旧数据误导 | 旧住民内容保留但不再增长；看板继续标注 AI 生成 |
| 浏览记录让人更在意“谁来看过” | 默认只显示数量与名单，不推送；清醒模式明确标注这些是 AI；防沉迷机制照常 |
| 记忆越存越多、检索变慢 | 每人独立上限（默认 400）、归档机制、FTS5 索引；无上限是用户主动选择 |
| 工具调用无限循环/卡死 | 8 轮上限 + 20 秒总超时 + 失败降级预检索 |
| web_search 泄露隐私或产生费用 | 默认关闭；只发送搜索词不发帖子原文；结果只留摘要与来源 |
| 本地生图头像风格失控 | 固定提示词模板 + 人工筛选后再入库，不在运行期生成 |
| 用户把 AI 当真人 | 底部合规提示、清醒模式、防沉迷与心理安全机制不变 |
