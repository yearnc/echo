# 《回响 Echo》阶段 B 实施计划

> 依据：《回响 Echo》双模式集成版 APP 规划书 v2.1（§15 开发路线图 · 阶段 B）
> 范围：阶段 B —— 完整单机版
> 日期：2026-09-19
> 目标一句话：**让社区自己活着** —— 住民有自己的动态、关系、记忆与私信，内容可以由用户自己的模型生成，也可以在没有网络、没有 API Key 的机器上照常跑完整流程。

---

## 0. 起点：阶段 A 实际交付了什么

先把家底数清楚（以下数字是 2026-09-19 对着代码核过的，与旧文档有出入处以本节为准）：

| 项 | 阶段 A 结束时的实际值 |
|---|---|
| 数据库 | `schemaVersion = 8`，**16 张表** |
| 代码规模 | `lib/` 81 个 Dart 文件（不含生成的 `.g.dart`），约 13.3k 行 |
| 测试 | `test/` 12 个文件约 2.0k 行；最后一次全量基线 **108 个测试全过** |
| 预置住民 | **24 个**（`assets/personas/personas.json`），已超过旧文档记的 12 个 |
| 内容来源 | 住民评论 = JSON 里 `commentSamples` 随机取；语音 = 预置音频 + 静态波形；客观分析 = 预置文本 |
| 调度 | 发帖排期（0—48h）+ 冷启动补发 + 前台心跳（策划 1 秒 / 随机 30 拍两档）；**无系统级后台任务** |
| 模式 | 回响 / 清醒双模式完整：切换归档、年龄门、永久提示、合规小字、防沉迷、心理安全均已落地 |
| 模型 | **只做探测**（连通性 / 鉴权 / 模型列表 / 测试对话），不生成任何业务内容 |
| 语音输入 | 无（`just_audio` 只负责播放预置音频） |
| 发布 | `v1.0.0` release 已打，真机安装通过 |

一句话概括：阶段 A 的社区是**单向**的 —— 住民会回应你，但他们自己没有生活。

## 1. 阶段 B 范围界定

### 1.1 规划书 §15「阶段 B」逐条对账

| 0—48 小时随机调度 | ✅ 本地队列 + 心跳 | 扩展到住民动态与私信 |
| 本地通知 | ✅ 已有 | 扩通知类型（关注 / 私信 / 热榜）+ 聚合 |
| 语音评论 + 转文字 | ❌ 预置音频 + 静态波形 | **真实 TTS / STT** |
| 表情包 | 🟡 素材库与导入已做 | 住民专属偏好 + AI 发图片评论 |
| 数据看板 | ❌ 未做 | **新建** |
| 防沉迷 | ✅ 计数 + 阈值 + 冷静模式 | 补「亮屏等待」与趋势曲线 |
| 心理安全 | ✅ 已做 | 补未成年人保护模式 |
| 私信、关注、热榜、话题 | ❌ 未做 | **全部新建** |
| 30+ AI 人格 | 🟡 已有 24 个 | 补到 30+，加圈层 / 作息 / 生活轨迹 |
| 关系与记忆 | ❌ 只有表设计 | **新建** |
| AI 住民自主发帖、动态、关系网 | ❌ 未做 | **新建（B 阶段主线）** |

### 1.2 做（阶段 B 验收范围内的）

1. **AI 住民的世界**：自主发帖、动态、互为点赞评论 @、关系网
2. **关系与记忆**：亲密度分级、记忆摘要、引用过去、连续剧情
3. **私信、关注、粉丝、消息页**
4. **话题、热榜、校园事件、社区时间感**
5. **楼中楼追问**
6. **真实语音**：TTS 语音评论 + STT 输入转写
7. **内容生成层**：接用户自己的模型，含离线样本兜底
8. **数据看板**
9. **系统级后台调度**（WorkManager / BGTaskScheduler）
10. **30+ 住民扩编**（含圈层与生活轨迹）
11. **未成年人保护模式**、每周反思报告的情绪维度

### 1.3 不做（推给阶段 C）

- 多模型并行（同一功能换模型跑）、云端同步、独立情绪分析报告
- 自定义表情包导入的高级形态（AI 生成表情包）
- 应用商店合规材料（隐私标签、深度合成标识申报、上架流程）
- 性能优化专项、iOS 真机验证（无设备）
- SQLCipher 全库加密（当前只加密 API Key，是否升级观望后再定）

> **范围纪律**：B 阶段不再为微视频拍摄做取舍 —— 片子已经拍完了。这一阶段按产品本身的完整性推进，
> 但**策划模式不能被冷落**：它是拍摄留下的资产，仍然要保持可用（住民自主发帖不该污染脚本排期的语义）。

## 2. 主线：从「帖子被回应」到「社区自己活着」

B 阶段跟 A 阶段的分界线，一张表说清：

| 维度 | 阶段 A | 阶段 B |
|---|---|---|
| 住民有没有自己的生活 | 没有，只在你的帖子下出现 | 有动态、有课表、有朋友、有作息 |
| 内容从哪来 | JSON 样本库随机取 | 用户自己的模型生成，样本库兜底 |
| 互动方向 | 单向（他们回应你） | 双向（他们互相之间也聊） |
| 记忆 | 无 | 记得你发过什么、关系多亲近 |
| 声音 | 预置音频 | 真 TTS |
| 时间感 | 只在你自己的帖子内 | 社区有自己的时间线（早晚不同） |

**验收这个故事讲没讲成的办法**：打开首页，如果刷出来的东西里有一半不是你发的，
而且那里面有两三个人在互相聊天——B 阶段就成立了。

## 3. 关键设计决策（动手前先定下这五条）

### 决策 1：内容生成走「生成器 + 样本兜底」，不让模型成为门槛

现状：住民评论是 `personas.json` 里 `commentSamples` 随机抽一条（`InteractionPlanner` 里那几行）。

B 阶段抽象成一个接口：

```dart
/// 所有业务内容的唯一出口。实现有两个：离线样本、用户自己的模型。
abstract class ContentGenerator {
  /// 住民对某条帖子发表评论
  Future<GeneratedComment> comment({
    required AiPersona persona,
    required Post post,
    required ConversationContext context, // 已有评论 / 是否楼中楼
  });

  /// 住民自己发一条动态
  Future<PostDraft> residentPost({
    required AiPersona persona,
    required WorldContext world,          // 时间、地点、校园事件
  });

  /// 住民私信
  Future<GeneratedMessage> directMessage({
    required AiPersona persona,
    required ConversationContext context,
  });
}
```

两个实现：

| 实现 | 来源 | 特点 |
|---|---|---|
| `SampleContentGenerator` | 现有 `commentSamples` + 模板拼装 | 离线、零成本、可测、结果稳定 |
| `ModelContentGenerator` | `model_configs` 里的配置，dio 调 OpenAI 兼容接口 | 贴合人格与上下文，需要 Key 与网络 |

设置里加一项：**内容生成 = 本地样本 / 我的模型**（默认本地样本）。

为什么这是 B 阶段最重要的决定：

1. 没配 Key 的人也能完整用 APP —— 这是本地优先原则的延伸；
2. 开发与测试全程离线跑得动，CI 不依赖网络；
3. **所有 B 阶段功能可以先用样本把架子搭完**，模型接上去只是换一个实现，不用等功能层；
4. 录屏、演示、给老师看的时候不会因为网络抖动翻车。

代价：`SampleContentGenerator` 要足够"像样"（比如楼中楼追问得能接上上一句），
否则大家会以为功能没做完。这部分工作量不能省。

### 决策 2：住民的动态是「预生成 + 排期」，不是「到点现生成」

理由与阶段 A 的调度决策同源：到点现生成意味着**断网就没有社区**，
而且同一条动态刷新两次会看到两个版本。

所以住民动态在**排期时就写进库**（0—48h 摊开，或按社区时间段排），到点由心跳 / 冷启动兑现。
生成失败（模型超时、报错）时**降级到样本**，而不是跳过 —— 社区不该因为 API 报错就静默一片。

### 决策 3：住民自己的动态也进 `posts` 表，不另开一张表

`posts` 加一个 `author_persona_id`（用户发的为 `null`），`is_ai_generated = 1`、`scope = echo`。

理由：信息流、帖子详情、评论区、点赞计数、`ai_interactions` 的外键全部现成，
"谁发的"只多一个字段。另开一张 `resident_posts` 表意味着上面每一样都要写第二遍，
而且信息流要做联合查询。**这一条能省掉一大块改动。**

### 决策 4：楼中楼是「有上下文才有的追问」

阶段 A 明确禁止"一个住民在同一条帖子下留两条评论"（会立刻暴露 AI 身份），
所以追问被推到了 B 阶段。要成立的前提是**上下文真的存在**：

- 数据层 `ai_interactions.parent_id` 字段已经有了，不用改表；
- 缺的是把「帖子 + 父评论 + 这个人的立场」组装成上下文喂给生成器；
- 排期规则：**同一住民在同一层楼里可以再评一次，但必须有上文**，且深度不超过 2 层。

所以楼中楼排在内容生成层之后（B7），不能提前做。

### 决策 5：记忆存摘要，不存聊天记录

`ai_relationships.memory_summary` 存的是几句压缩过的「我记得你…」，不是全量历史。

理由：① token 成本；② 隐私 —— 用户的帖文不该被整段搬进每一次请求。

更新时机：一次互动结束之后**异步**更新摘要，失败不影响互动本身。

### 决策 6：系统级后台调度接进来，但冷启动补发必须保留

WorkManager / BGTaskScheduler 是"锦上添花"，不是地基。安卓厂商的省电策略一定会杀后台任务 ——
这是前提，不是 bug。

所以系统级调度的验收标准不是「通知准时到」，而是「**没准时到的时候，打开 APP 一定会补上**」。

## 4. 数据层扩展（schema v8 → v9）

新增表（沿用规划书 §8 的字段设计，此处只列要点）：

```sql
-- ① AI 关系：亲密度与记忆摘要（规划书 §8 已设计，B 阶段落地）
CREATE TABLE ai_relationships (
  id TEXT PRIMARY KEY,
  persona_id TEXT NOT NULL,
  relationship_level INTEGER DEFAULT 0,   -- 陌生→眼熟→互关→熟人→好友
  intimacy INTEGER DEFAULT 0,
  last_interaction_at INTEGER,
  memory_summary TEXT,                    -- 压缩后的「我记得你…」
  follow_state TEXT,                      -- 谁关注了谁
  scope TEXT DEFAULT 'echo'
);

-- ② 私信
CREATE TABLE private_messages (
  id TEXT PRIMARY KEY,
  persona_id TEXT NOT NULL,
  direction TEXT NOT NULL,                -- in / out
  content TEXT,
  media_type TEXT,                        -- text / voice / sticker / image
  voice_path TEXT,
  transcript TEXT,
  created_at INTEGER NOT NULL,
  read_at INTEGER,
  scope TEXT DEFAULT 'echo'
);

-- ③ 话题
CREATE TABLE topics (
  id TEXT PRIMARY KEY, name TEXT NOT NULL, description TEXT,
  heat INTEGER DEFAULT 0, is_built_in INTEGER DEFAULT 0,
  created_at INTEGER, deleted_at INTEGER, scope TEXT DEFAULT 'shared'
);
-- **刻意没有 post_topics**（2026-09-19 实施时砍掉的）：一条帖子只挂一个话题
-- （发布页就是单选），现有的 posts.topic_id 已经够表达。多对多是跟着
-- "一条帖子挂多个话题"这个还不存在的需求来的，等它真出现再开不迟。

-- ④ 住民的生活轨迹（哪个点在哪、在干什么）
CREATE TABLE persona_routines (
  id TEXT PRIMARY KEY, persona_id TEXT NOT NULL,
  hour INTEGER NOT NULL, place TEXT, activity TEXT
);
```

**改动既有表的地方只有两处**：

| 表 | 改动 | 说明 |
|---|---|---|
| `posts` | 加 `author_persona_id TEXT`、`place TEXT`（可选） | 区分用户帖与住民帖（决策 3）；`place` 支撑"图书馆/食堂"这类地点标签 |
| `ai_personas` | 加 `circle TEXT`（圈层）、`bio_long TEXT` | 圈层用于信息流的"同校/兴趣"，长简介给个人主页 |

**索引与外键**照规划书 §8；`private_messages.persona_id`、`posts.author_persona_id` 建索引。

**迁移要求**：老库（有真实用户数据的）必须能升上来，不能重建。迁移测试要覆盖"v8 库升到 v9 后
帖子 / 互动 / 设置 / 记录全在"。

## 5. 里程碑

> 顺序是依赖顺序，不是时间顺序。B1 是绝大多数事情的前置；B8（语音）与 B10（系统调度）可以并行开工。

### B1 · 数据地基

**交付物**：§4 的全部新表与字段；`AiRelationshipRepository` / `PrivateMessageRepository` /
`TopicRepository` / `PersonaRoutineRepository`；迁移到 v9；住民 24 → 30+ 的扩编（含圈层与作息）。

**验收**：老库升级后数据零丢失；新仓储单测齐；信息流能显示住民发的帖子（手工插一条验证）。

**依赖**：无。

---

### B2 · 内容生成层

**交付物**：

- `domain/services/content_generator.dart`：`ContentGenerator` 接口 + `SampleContentGenerator` + `ContentSource`（选路与降级）
- `domain/services/model_content_generator.dart`：读 `model_configs`，dio 调用，超时 / 错误码映射 / 降级
- **人格提示词组装**：身份 + 语气 + 说话方式 + 帖子正文（活跃时段与关系等级要等 B4 有了数据再喂）

> **实施时砍掉的两条**（2026-09-19）：
> ① **设置项「内容生成来源」没了** —— 自动选路：配了模型就用模型，没配就用样本。
> 配了模型本来就是为了用它，再多一个开关只多一个要理解的概念。
> ② **"本地缓存"改成了"只调用一次 + 覆盖还没兑现的"** —— 生成发生在发帖之后，
> 排期那一步已经用预置台词把内容填好了，所以没有"同一条重复生成"的机会。

**验收**：配真实 Key 能生成一条贴合人格的评论；删掉 Key 后全部功能照常走样本；
超时 / 401 / 429 各自降级到样本且不崩；提示词组装是纯函数、有单测。

**依赖**：B1（要读关系与记忆）。

---

### B3 · 住民的世界（B 阶段主线）

**交付物**：

- **住民动态流**：信息流的「推荐 / 同校」里混入住民自己的帖子
- **住民个人主页**：资料、他的动态、关注 / 粉丝、关系等级
- **住民之间互相互动**：点赞、评论、@（预生成排期，决策 2）
- **世界 tick**：心跳与冷启动时给住民排一小批动态，按社区时间段分布

**验收**：杀掉 APP 再打开，能看到这几个小时里住民发的新帖；住民之间出现对话；
某住民主页上能看到他和你、和别人的互动记录。

**依赖**：B1、B2。

---

### B4 · 关系与记忆

**交付物**：

- 关系等级推进规则（陌生 → 眼熟 → 互关 → 熟人 → 好友），**纯逻辑可测**
- 记忆摘要的生成与更新（异步、失败不影响主流程）
- 评论与私信里引用过去（"你上次拍的那张天空照挺好看的"）
- 连续剧情：几天后的追问

**验收**：连续发 3 条帖之后，住民评论能引用旧帖内容；关系等级会影响语气与互动频率；
摘要更新失败时互动本身不受影响（有测试守住）。

**依赖**：B2、B3。

---

### B5 · 私信、关注与消息页

**交付物**：

- 会话列表 + 会话详情（文字 / 表情包 / 语音）
- **底部导航加「消息」**（回响模式：首页 / 发布 / 消息 / 通知 / 我的，对齐规划书 §5.1）
- 关注 / 粉丝页
- 通知类型扩展（关注 / 私信 / 转发）+ 聚合（"5 位社区住民互动了你的帖子"）

**验收**：住民会主动私信；未读红点准确；通知点击跳对页面。

**依赖**：B1、B2。

**注意**：规划书 §3.5 明确删掉了「对方正在输入…」，做私信时**不要顺手加回来**。

---

### B6 · 话题、热榜与时间感

**交付物**：

- 话题：发帖可加话题、话题页、话题详情
- 热榜：今日热门帖子 / 热门话题 / 活跃住民（**算法写成纯函数**）
- 校园事件：考试周、降温、停电、节日（按日期触发）
- 社区时间感：早晨晨跑、中午食堂、傍晚球场、深夜树洞，动态类型随时段不同
- 信息流标签全部可用：推荐 / 关注 / 同校 / 热榜 / 话题 / 搜索

**验收**：热榜排序有单测（含并列与空数据的边界）；同一时段打开 APP 看到的社区氛围符合设定。

**依赖**：B1、B3。

---

### B7 · 楼中楼追问

**交付物**：

- 评论区楼中楼 UI 与数据（`parent_id` 已有）
- 追问排期规则：有上文才允许同一住民再评一次，最多 2 层
- 上下文组装：父评论 + 之前的往返

**验收**：追问看起来像对话，而不是两个人各说一句；同一住民不会在同一层平铺两条无关评论。

**依赖**：B2（上下文组装）、B3。

---

### B8 · 真实语音（可与 B3—B7 并行）

**交付物**：

- TTS 接入（系统 TTS 优先，离线可用），按人格分音色
- 语音评论生成 → 存本地文件 → 时长 / 波形 → 转写文本
- STT：用户语音输入转文字
- 播放器底部「AI 生成语音」小字（合规，不可省）

**验收**：住民语音条能真的播出声音；飞行模式下已生成的语音仍能播；转写文本与语音内容一致。

**依赖**：无（只要不与 B2 抢同一个生成接口）。

---

### B9 · 数据看板

**交付物**：

- 互动趋势：点赞 / 评论 / 粉丝变化
- 查看反馈次数、亮屏等待次数、互动高峰时段
- 固定标注：**「以下数据由 AI 生成，不代表真实社会评价」**
- 清醒模式只展示真实记录统计

**验收**：曲线跟着真实互动变化；两种模式下的看板内容不同；标注不可去掉。

### B2 · 内容生成层（2026-09-19 完成）

**接口**：`ContentGenerator.comments(personas, post) → {住民 id: 内容}`。
三个东西凑齐这件事：

| 角色 | 类 | 说明 |
|---|---|---|
| 接口 | `ContentGenerator` | 住民说的话的唯一出口 |
| 兜底 | `SampleContentGenerator` | 从住民自己的预置台词里挑；另有**同步**方法——兜底不该还有自己的失败可能 |
| 主路 | `ModelContentGenerator` | 一次请求写完整批，静态的提示词组装与 JSON 解析 |
| 选路 | `ContentSource` | 有模型走模型，失败/超时/返回空一律退回样本 |

**关键决定：生成发生在"排期之后、兑现之前"，不是发布那一刻。**

发帖时 `InteractionPlanner`（纯逻辑、不联网）照旧用预置台词把内容填好并落库，
发布流程**不等模型**；落库之后 `unawaited(scheduler.upgradeCommentsWithModel(postId))`
才在后台把还没兑现的那些换成模型写的。这么排的好处：发帖不卡（写五条评论要好几秒）、
排期里永远有兜底内容（模型挂了社区照样有人说话）、已经兑现的不动（评论不在用户眼皮底下变）。

**一次请求写整批，不逐条调用**：一次发帖五到八条评论，逐条就是五到八次往返；而且同一批
一起写出来的能互相避开同一句话——"这张天空照真好看"被三个人说，一眼就是假的。

**模型写的东西也要过本地词表**：住民里有"毒舌调侃型"，让它自由发挥有风险；命中就把
那一条丢回预置台词。这里**不调模型审核**（那等于每条评论花两次钱）。

**砍掉设置开关的后果**：用户不必选"用样本还是用模型"，配了模型就是它在写。

**踩到的坑**：`insertPlanned` 的排期 id 是「帖子 + 序号」，所以同一条帖子只能排一次期——
写测试时一天里给同一条帖子排了两次，主键直接撞上了。产品代码里没有这个问题
（发帖只排一次），加注释记下了。

**基线**：175 个测试全过（新增 24 个）、`flutter analyze` 零问题。

**仍然敞着的**：

1. `upgradeCommentsWithModel` 是 fire-and-forget，切到清醒模式也拦不住它，会白花一次调用
2. 生成的评论只过本地词表，没走模型审核

### B3 · 住民的世界（2026-09-19 完成）

**这是那条分界线**：从这一版起，住民不再只在你的帖子底下出现。

| 做了什么 | 在哪儿 |
|---|---|
| 住民自己发动态（内容） | `ContentGenerator.residentPosts`：样本按**圈层模板 + 作息**拼，模型一次写整批 |
| 世界的钟 | `WorldService.tick()`：冷启动 + 心跳的 30 秒档各查一次 |
| 住民之间互相串门 | `_schedulePeers`：每条动态排 0—2 条邻居的评论 |
| 住民主页 | `/resident/:id`：资料、作息、他发过的动态 |
| 入口 | 信息流卡片、帖子详情、评论区的头像与名字都能点开 |
| 通知的分寸 | 兑现时先查帖主——**住民动态底下的互动不通知用户** |

**关键决定：动态"发生"在过去，而不是"刚刚"。**

tick 不是"现在生成一条，时间戳打现在"，而是先把 `[上次水位, 现在]` 这一段切开，
再让每个人落在其中一个时刻上。所以隔了一夜打开 APP，看到的是一夜之间陆续发生的
事，而不是一屏时间戳相同的"刚刚"。水位存在 `app_settings.world.lastTickAt`，
首次运行时只记不生成——空信息流是新用户的真实起点（阶段 A 定的），一进门就冒出
五条别人的动态会把这个起点冲掉。

**一次最多补四条**。走了再久也不一口气灌进来：那不是"社区热闹"，那是刷屏。

**住民动态的评论用样本，不走模型**：动态本身已经是一次模型调用了，底下的串门
是配角，不值得再花一次钱。

**踩到的坑（一个真 bug，而且是阶段 A 埋下的）**：
`PostRepository` 的 id 生成写着"时间戳 + 随机后缀"，但那个"随机"其实是
`时间戳.remainder(max)`——**拿时间戳当随机数**。用户手动发帖一次只插一条，撞不上；
世界 tick 一次要连着写好几条，同一毫秒内时间戳相同、后缀也相同，主键当场冲突。
已改成 `dart:math` 的 `Random`。

**基线**：190 个测试全过（新增 15 个）、`flutter analyze` 零问题。

**仍然敞着的**：

1. 住民主页还没有"你和他关系到哪一步了"——那要等 B4 的关系表有数据
2. 住民动态只有文字（图片素材还没有）
3. 住民之间的 @、转发、互相关注还没做

### B3.5 · 住民的形象（2026-09-19 定，B3 的续篇）

> **起因**：住民有了自己的生活（B3），接下来该有"自己的样子"。
> 这一节是 B3 之后提的想法：让住民能用文生图模型换头像、发图文帖、
> 顺带改自己的签名。
>
> **文生视频明确不做**：贵一个量级、慢到分钟级，而且普通学生发视频的频率
> 本来就低——做了反而假。

**按"表达渠道的重量"分层，先轻后重**：

| 层次 | 成本 | 风险 | 顺序 |
|---|---|---|---|
| 改**签名**（bio / 状态） | 极低（纯文本） | 无 | ① |
| 改**头像** | 高（一次文生图） | 中（用户认不出人） | ② |
| **图文帖** | 高 | 中 | ② 同批 |
| 改**昵称** | 极低 | **高** | ③ 最后，且必须留痕 |

签名先做，因为它是人最常用来表达心情的地方（QQ 状态、微信签名），
零成本，立刻有味道。头像最有效果但也最危险——**住民一旦频繁换脸，
社区"这些人一直在"的根基就松了**。

**关键决定**：

1. **模型配置分用途**（chat / image），允许只配其中之一。
   文生图和聊天通常不是同一家、同一个模型，硬要用一条配置是强人所难。
2. **换头像必须有理由**，不随机。真人换头像的时机就那么几种：
   心情转折（低落时换成暗的）、和你的关系走到某一步（要等 B4）、
   校园事件（要等 B6）。随机换头像 = "程序在动"。
3. **一个 tick 最多一张图**，再加概率打折，一天下来 1—2 张。
   图像生成比文本贵一个量级。
4. **图必须"像手机随手拍的"**：构图上乘、光影完美的 AI 图会立刻露馅，
   真人发的都是模糊的、歪的、带噪点的。prompt 里要死死压住这条，
   甚至主动加轻微模糊。
5. **人物一致性不用操心**：住民发的是"他看到的东西"（风景、食物、座位），
   不是自拍，所以不存在"同一个住民的图里人长得不一样"的问题。
6. **生成的图也过审核**：prompt 是我们自己写的、跑偏概率低，
   但配了多模态模型时仍然审一次。

**图文帖的触发（按"值不值得拍"筛）**：

- routine 里有值得拍的场景：操场、食堂、湖边、图书馆靠窗。
  宿舍睡觉不值得拍——按 place 白名单筛，或者给 `persona_routines` 加标记
- 私信里的"给你看看"（B5 之后最自然，因为本来就是一问一答）
- 换头像时顺手发一条："换了个新头像，最近心情不错"

**技术上的两块底座**（这一节的主要工作量）：

- `model_configs` 加用途列；`ModelGateway` 多一条生成图片的通道
- 住民从"只读的内容资产"变成"有当前状态"：`ai_personas` 表里那份是
  当前值，`assets/personas.json` 里那份退回成出厂值。住民改过签名或头像之后，
  读的时候以表为准

### 顺带补上的：用户也能说话了（2026-09-19）

实测时发现有件事一直缺着：**评论区底下那对"♡ 0"和"回复"是死的**——
从阶段 A 起就是纯装饰，只是个能点的样子。而信息流里点不动赞。

社区是单向的：住民在说话，用户只能看着。B3 之后住民的动态进了信息流，
这件事就遮不住了。

| 补的东西 | 落在哪儿 |
|---|---|
| 给帖子点赞 | `posts.liked_at`：一人一条帖子一颗心，直接记在帖子那一行上 |
| 给评论点赞 | 单独一张 `comment_likes`——评论有很多条，而且点的可能是住民的、也可能是我自己的 |
| 自己的评论 | 新表 `user_comments`，与 `ai_interactions` 分开 |
| 回复某一条 | `user_comments.parent_id` + `reply_to_name` |

**为什么用户的评论不塞进 `ai_interactions`**：那张表是"排期与兑现"的队列
（`scheduled_at` / `status` / 取消 / 补发），而"我刚回了句什么"没有这些事。
分开存，合并发生在读取那一层——一个 UNION 让数据库把两条来源排成一条时间线。

**迁移踩的坑（值得记）**：`user_comments` 是 v11 建的，`parent_id` 是 v12 加的；
但 Drift 的 `createTable` 用的永远是**当前**的表定义，所以从 v10 及更早升上来时，
v11 那一块建出来的表**已经带着** v12 才该有的列，v12 再 `addColumn` 就是
`duplicate column name`——老库和新装用户都会在启动时炸。
修法是让 v12 的那两句只在 `from >= 11` 时执行。

**这个坑是被迁移测试抓住的**（那是一个真的 v8 库一路升上来的测试）——
如果只测"新库能不能建起来"，它会一路绿到用户手机上。

**另外一个来由**：这一版最初在帖子详情页给点赞做了个带边框的胶囊按钮，
实测时被一句话点破——"为什么又新加了一个小卡片来显示点赞，冗余了"。
同一个动作在两处长得不一样，用户会以为是两件事。已改回与信息流一致的那颗心。

**基线**：217 个测试全过、`flutter analyze` 零问题。

**顺带补上的主题注脚**：住民"给自己生成头像"这件事，正好是戈夫曼那个
前台/后台的镜像——用户在精心挑选自己的网络形象，AI 住民在做一模一样的事，
甚至更彻底（连照片都是生成的）。规划书 §14 那张映射表里"戈夫曼前台/后台"
这一条，本来只有"发帖、修图"几个落点，住民换头像能把它补成闭环：
**你精心打造的形象，和 AI 随手生成的形象，本质上是同一件事**。

### 已提前落地（2026-09-19，B1 之前）

开工前先补的两件事，都属规划书 §6.10「心理安全与未成年人保护」里的
"内容审核与安全过滤"（B2 的"生成内容同样受过滤"约束也靠它）：
