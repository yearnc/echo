# 《回响 Echo》阶段 B 实施计划

> 依据：《回响 Echo》双模式集成版 APP 规划书 v2.1（§15 开发路线图 · 阶段 B）
> 范围：阶段 B —— 完整单机版
> 日期：2026-09-19
> 目标一句话：**让社区自己活着** —— 住民有自己的动态、关系、记忆与私信，内容可以由用户自己的模型生成，也可以在没有网络、没有 API Key 的机器上照常跑完整流程。

---

## 0. 起点：阶段 A 实际交付了什么

先把家底数清楚（以下数字是 2026-09-19 对着代码核过的，与旧文档有出入处以本节为准）：

| 项 | 阶段 A 结束时的实际值 |
|---|---|
| 数据库 | `schemaVersion = 8`，**16 张表** |
| 代码规模 | `lib/` 81 个 Dart 文件（不含生成的 `.g.dart`），约 13.3k 行 |
| 测试 | `test/` 12 个文件约 2.0k 行；最后一次全量基线 **108 个测试全过** |
| 预置住民 | **24 个**（`assets/personas/personas.json`），已超过旧文档记的 12 个 |
| 内容来源 | 住民评论 = JSON 里 `commentSamples` 随机取；语音 = 预置音频 + 静态波形；客观分析 = 预置文本 |
| 调度 | 发帖排期（0—48h）+ 冷启动补发 + 前台心跳（策划 1 秒 / 随机 30 拍两档）；**无系统级后台任务** |
| 模式 | 回响 / 清醒双模式完整：切换归档、年龄门、永久提示、合规小字、防沉迷、心理安全均已落地 |
| 模型 | **只做探测**（连通性 / 鉴权 / 模型列表 / 测试对话），不生成任何业务内容 |
| 语音输入 | 无（`just_audio` 只负责播放预置音频） |
| 发布 | `v1.0.0` release 已打，真机安装通过 |

一句话概括：阶段 A 的社区是**单向**的 —— 住民会回应你，但他们自己没有生活。

| 语音评论 + 转文字 | ❌ 预置音频 + 静态波形 | **真实 TTS / STT** |
| 表情包 | 🟡 素材库与导入已做 | 住民专属偏好 + AI 发图片评论 |
| 数据看板 | ❌ 未做 | **新建** |
| 防沉迷 | ✅ 计数 + 阈值 + 冷静模式 | 补「亮屏等待」与趋势曲线 |
| 心理安全 | ✅ 已做 | 补未成年人保护模式 |
| 私信、关注、热榜、话题 | ❌ 未做 | **全部新建** |
| 30+ AI 人格 | 🟡 已有 24 个 | 补到 30+，加圈层 / 作息 / 生活轨迹 |
| 关系与记忆 | ❌ 只有表设计 | **新建** |
| AI 住民自主发帖、动态、关系网 | ❌ 未做 | **新建（B 阶段主线）** |

### 1.2 做（阶段 B 验收范围内的）

1. **AI 住民的世界**：自主发帖、动态、互为点赞评论 @、关系网
2. **关系与记忆**：亲密度分级、记忆摘要、引用过去、连续剧情
3. **私信、关注、粉丝、消息页**
4. **话题、热榜、校园事件、社区时间感**
5. **楼中楼追问**
6. **真实语音**：TTS 语音评论 + STT 输入转写
7. **内容生成层**：接用户自己的模型，含离线样本兜底
8. **数据看板**
9. **系统级后台调度**（WorkManager / BGTaskScheduler）
10. **30+ 住民扩编**（含圈层与生活轨迹）
11. **未成年人保护模式**、每周反思报告的情绪维度

### 1.3 不做（推给阶段 C）

- 多模型并行（同一功能换模型跑）、云端同步、独立情绪分析报告
- 自定义表情包导入的高级形态（AI 生成表情包）
- 应用商店合规材料（隐私标签、深度合成标识申报、上架流程）
- 性能优化专项、iOS 真机验证（无设备）
- SQLCipher 全库加密（当前只加密 API Key，是否升级观望后再定）

> **范围纪律**：B 阶段不再为微视频拍摄做取舍 —— 片子已经拍完了。这一阶段按产品本身的完整性推进，
> 但**策划模式不能被冷落**：它是拍摄留下的资产，仍然要保持可用（住民自主发帖不该污染脚本排期的语义）。

## 2. 主线：从「帖子被回应」到「社区自己活着」

B 阶段跟 A 阶段的分界线，一张表说清：

| 维度 | 阶段 A | 阶段 B |
|---|---|---|
| 住民有没有自己的生活 | 没有，只在你的帖子下出现 | 有动态、有课表、有朋友、有作息 |
| 内容从哪来 | JSON 样本库随机取 | 用户自己的模型生成，样本库兜底 |
| 互动方向 | 单向（他们回应你） | 双向（他们互相之间也聊） |
| 记忆 | 无 | 记得你发过什么、关系多亲近 |
| 声音 | 预置音频 | 真 TTS |
| 时间感 | 只在你自己的帖子内 | 社区有自己的时间线（早晚不同） |

**验收这个故事讲没讲成的办法**：打开首页，如果刷出来的东西里有一半不是你发的，
而且那里面有两三个人在互相聊天——B 阶段就成立了。

## 3. 关键设计决策（动手前先定下这五条）

### 决策 1：内容生成走「生成器 + 样本兜底」，不让模型成为门槛

现状：住民评论是 `personas.json` 里 `commentSamples` 随机抽一条（`InteractionPlanner` 里那几行）。

B 阶段抽象成一个接口：

```dart
/// 所有业务内容的唯一出口。实现有两个：离线样本、用户自己的模型。
abstract class ContentGenerator {
  /// 住民对某条帖子发表评论
  Future<GeneratedComment> comment({
    required AiPersona persona,
    required Post post,
    required ConversationContext context, // 已有评论 / 是否楼中楼
  });

  /// 住民自己发一条动态
  Future<PostDraft> residentPost({
    required AiPersona persona,
    required WorldContext world,          // 时间、地点、校园事件
  });

  /// 住民私信
  Future<GeneratedMessage> directMessage({
    required AiPersona persona,
    required ConversationContext context,
  });
}
```

两个实现：

| 实现 | 来源 | 特点 |
|---|---|---|
| `SampleContentGenerator` | 现有 `commentSamples` + 模板拼装 | 离线、零成本、可测、结果稳定 |
| `ModelContentGenerator` | `model_configs` 里的配置，dio 调 OpenAI 兼容接口 | 贴合人格与上下文，需要 Key 与网络 |

设置里加一项：**内容生成 = 本地样本 / 我的模型**（默认本地样本）。

为什么这是 B 阶段最重要的决定：

1. 没配 Key 的人也能完整用 APP —— 这是本地优先原则的延伸；
2. 开发与测试全程离线跑得动，CI 不依赖网络；
3. **所有 B 阶段功能可以先用样本把架子搭完**，模型接上去只是换一个实现，不用等功能层；
4. 录屏、演示、给老师看的时候不会因为网络抖动翻车。

代价：`SampleContentGenerator` 要足够"像样"（比如楼中楼追问得能接上上一句），
否则大家会以为功能没做完。这部分工作量不能省。

### 决策 2：住民的动态是「预生成 + 排期」，不是「到点现生成」

理由与阶段 A 的调度决策同源：到点现生成意味着**断网就没有社区**，
而且同一条动态刷新两次会看到两个版本。

所以住民动态在**排期时就写进库**（0—48h 摊开，或按社区时间段排），到点由心跳 / 冷启动兑现。
生成失败（模型超时、报错）时**降级到样本**，而不是跳过 —— 社区不该因为 API 报错就静默一片。

### 决策 3：住民自己的动态也进 `posts` 表，不另开一张表

`posts` 加一个 `author_persona_id`（用户发的为 `null`），`is_ai_generated = 1`、`scope = echo`。

理由：信息流、帖子详情、评论区、点赞计数、`ai_interactions` 的外键全部现成，
"谁发的"只多一个字段。另开一张 `resident_posts` 表意味着上面每一样都要写第二遍，
而且信息流要做联合查询。**这一条能省掉一大块改动。**

### 决策 4：楼中楼是「有上下文才有的追问」

阶段 A 明确禁止"一个住民在同一条帖子下留两条评论"（会立刻暴露 AI 身份），
所以追问被推到了 B 阶段。要成立的前提是**上下文真的存在**：

- 数据层 `ai_interactions.parent_id` 字段已经有了，不用改表；
- 缺的是把「帖子 + 父评论 + 这个人的立场」组装成上下文喂给生成器；
- 排期规则：**同一住民在同一层楼里可以再评一次，但必须有上文**，且深度不超过 2 层。

所以楼中楼排在内容生成层之后（B7），不能提前做。

### 决策 5：记忆存摘要，不存聊天记录

`ai_relationships.memory_summary` 存的是几句压缩过的「我记得你…」，不是全量历史。

理由：① token 成本；② 隐私 —— 用户的帖文不该被整段搬进每一次请求。

更新时机：一次互动结束之后**异步**更新摘要，失败不影响互动本身。

### 决策 6：系统级后台调度接进来，但冷启动补发必须保留

WorkManager / BGTaskScheduler 是"锦上添花"，不是地基。安卓厂商的省电策略一定会杀后台任务 ——
这是前提，不是 bug。

所以系统级调度的验收标准不是「通知准时到」，而是「**没准时到的时候，打开 APP 一定会补上**」。

## 4. 数据层扩展（schema v8 → v9）

新增表（沿用规划书 §8 的字段设计，此处只列要点）：

```sql
-- ① AI 关系：亲密度与记忆摘要（规划书 §8 已设计，B 阶段落地）
CREATE TABLE ai_relationships (
  id TEXT PRIMARY KEY,
  persona_id TEXT NOT NULL,
  relationship_level INTEGER DEFAULT 0,   -- 陌生→眼熟→互关→熟人→好友
  intimacy INTEGER DEFAULT 0,
  last_interaction_at INTEGER,
  memory_summary TEXT,                    -- 压缩后的「我记得你…」
  follow_state TEXT,                      -- 谁关注了谁
  scope TEXT DEFAULT 'echo'
);

-- ② 私信
CREATE TABLE private_messages (
  id TEXT PRIMARY KEY,
  persona_id TEXT NOT NULL,
  direction TEXT NOT NULL,                -- in / out
  content TEXT,
  media_type TEXT,                        -- text / voice / sticker / image
  voice_path TEXT,
  transcript TEXT,
  created_at INTEGER NOT NULL,
  read_at INTEGER,
  scope TEXT DEFAULT 'echo'
);

-- ③ 话题
CREATE TABLE topics (
  id TEXT PRIMARY KEY, name TEXT NOT NULL, description TEXT,
  heat INTEGER DEFAULT 0, is_built_in INTEGER DEFAULT 0,
  created_at INTEGER, deleted_at INTEGER, scope TEXT DEFAULT 'shared'
);
-- **刻意没有 post_topics**（2026-09-19 实施时砍掉的）：一条帖子只挂一个话题
-- （发布页就是单选），现有的 posts.topic_id 已经够表达。多对多是跟着
-- "一条帖子挂多个话题"这个还不存在的需求来的，等它真出现再开不迟。

-- ④ 住民的生活轨迹（哪个点在哪、在干什么）
CREATE TABLE persona_routines (
  id TEXT PRIMARY KEY, persona_id TEXT NOT NULL,
  hour INTEGER NOT NULL, place TEXT, activity TEXT
);
```

**改动既有表的地方只有两处**：

| 表 | 改动 | 说明 |
|---|---|---|
| `posts` | 加 `author_persona_id TEXT`、`place TEXT`（可选） | 区分用户帖与住民帖（决策 3）；`place` 支撑"图书馆/食堂"这类地点标签 |
| `ai_personas` | 加 `circle TEXT`（圈层）、`bio_long TEXT` | 圈层用于信息流的"同校/兴趣"，长简介给个人主页 |

**索引与外键**照规划书 §8；`private_messages.persona_id`、`posts.author_persona_id` 建索引。

**迁移要求**：老库（有真实用户数据的）必须能升上来，不能重建。迁移测试要覆盖"v8 库升到 v9 后
帖子 / 互动 / 设置 / 记录全在"。

## 5. 里程碑

> 顺序是依赖顺序，不是时间顺序。B1 是绝大多数事情的前置；B8（语音）与 B10（系统调度）可以并行开工。

### B1 · 数据地基

**交付物**：§4 的全部新表与字段；`AiRelationshipRepository` / `PrivateMessageRepository` /
`TopicRepository` / `PersonaRoutineRepository`；迁移到 v9；住民 24 → 30+ 的扩编（含圈层与作息）。

**验收**：老库升级后数据零丢失；新仓储单测齐；信息流能显示住民发的帖子（手工插一条验证）。

**依赖**：无。

---

### B2 · 内容生成层

**交付物**：

- `domain/services/content_generator.dart`：`ContentGenerator` 接口 + `SampleContentGenerator` + `ContentSource`（选路与降级）
- `domain/services/model_content_generator.dart`：读 `model_configs`，dio 调用，超时 / 错误码映射 / 降级
- **人格提示词组装**：身份 + 语气 + 说话方式 + 帖子正文（活跃时段与关系等级要等 B4 有了数据再喂）

> **实施时砍掉的两条**（2026-09-19）：
> ① **设置项「内容生成来源」没了** —— 自动选路：配了模型就用模型，没配就用样本。
> 配了模型本来就是为了用它，再多一个开关只多一个要理解的概念。
> ② **"本地缓存"改成了"只调用一次 + 覆盖还没兑现的"** —— 生成发生在发帖之后，
> 排期那一步已经用预置台词把内容填好了，所以没有"同一条重复生成"的机会。

**验收**：配真实 Key 能生成一条贴合人格的评论；删掉 Key 后全部功能照常走样本；
超时 / 401 / 429 各自降级到样本且不崩；提示词组装是纯函数、有单测。

**依赖**：B1（要读关系与记忆）。

---

### B3 · 住民的世界（B 阶段主线）

**交付物**：

- **住民动态流**：信息流的「推荐 / 同校」里混入住民自己的帖子
- **住民个人主页**：资料、他的动态、关注 / 粉丝、关系等级
- **住民之间互相互动**：点赞、评论、@（预生成排期，决策 2）
- **世界 tick**：心跳与冷启动时给住民排一小批动态，按社区时间段分布

**验收**：杀掉 APP 再打开，能看到这几个小时里住民发的新帖；住民之间出现对话；
某住民主页上能看到他和你、和别人的互动记录。

**依赖**：B1、B2。

---

### B4 · 关系与记忆

**交付物**：

- 关系等级推进规则（陌生 → 眼熟 → 互关 → 熟人 → 好友），**纯逻辑可测**
- 记忆摘要的生成与更新（异步、失败不影响主流程）
- 评论与私信里引用过去（"你上次拍的那张天空照挺好看的"）
- 连续剧情：几天后的追问

**验收**：连续发 3 条帖之后，住民评论能引用旧帖内容；关系等级会影响语气与互动频率；
摘要更新失败时互动本身不受影响（有测试守住）。

**依赖**：B2、B3。

---

### B5 · 私信、关注与消息页

**交付物**：

- 会话列表 + 会话详情（文字 / 表情包 / 语音）
- **底部导航加「消息」**（回响模式：首页 / 发布 / 消息 / 通知 / 我的，对齐规划书 §5.1）
- 关注 / 粉丝页
- 通知类型扩展（关注 / 私信 / 转发）+ 聚合（"5 位社区住民互动了你的帖子"）

**验收**：住民会主动私信；未读红点准确；通知点击跳对页面。

**依赖**：B1、B2。

**注意**：规划书 §3.5 明确删掉了「对方正在输入…」，做私信时**不要顺手加回来**。

---

### B6 · 话题、热榜与时间感

**交付物**：

- 话题：发帖可加话题、话题页、话题详情
- 热榜：今日热门帖子 / 热门话题 / 活跃住民（**算法写成纯函数**）
- 校园事件：考试周、降温、停电、节日（按日期触发）
- 社区时间感：早晨晨跑、中午食堂、傍晚球场、深夜树洞，动态类型随时段不同
- 信息流标签全部可用：推荐 / 关注 / 同校 / 热榜 / 话题 / 搜索

**验收**：热榜排序有单测（含并列与空数据的边界）；同一时段打开 APP 看到的社区氛围符合设定。

**依赖**：B1、B3。

---

### B7 · 楼中楼追问

**交付物**：

- 评论区楼中楼 UI 与数据（`parent_id` 已有）
- 追问排期规则：有上文才允许同一住民再评一次，最多 2 层
- 上下文组装：父评论 + 之前的往返

**验收**：追问看起来像对话，而不是两个人各说一句；同一住民不会在同一层平铺两条无关评论。

**依赖**：B2（上下文组装）、B3。

---

### B8 · 真实语音（可与 B3—B7 并行）

**交付物**：

- TTS 接入（系统 TTS 优先，离线可用），按人格分音色
- 语音评论生成 → 存本地文件 → 时长 / 波形 → 转写文本
- STT：用户语音输入转文字
- 播放器底部「AI 生成语音」小字（合规，不可省）

**验收**：住民语音条能真的播出声音；飞行模式下已生成的语音仍能播；转写文本与语音内容一致。

**依赖**：无（只要不与 B2 抢同一个生成接口）。

---

### B9 · 数据看板

**交付物**：

- 互动趋势：点赞 / 评论 / 粉丝变化
- 查看反馈次数、亮屏等待次数、互动高峰时段
- 固定标注：**「以下数据由 AI 生成，不代表真实社会评价」**
- 清醒模式只展示真实记录统计

**验收**：曲线跟着真实互动变化；两种模式下的看板内容不同；标注不可去掉。

### B2 · 内容生成层（2026-09-19 完成）

**接口**：`ContentGenerator.comments(personas, post) → {住民 id: 内容}`。
三个东西凑齐这件事：

| 角色 | 类 | 说明 |
|---|---|---|
| 接口 | `ContentGenerator` | 住民说的话的唯一出口 |
| 兜底 | `SampleContentGenerator` | 从住民自己的预置台词里挑；另有**同步**方法——兜底不该还有自己的失败可能 |
| 主路 | `ModelContentGenerator` | 一次请求写完整批，静态的提示词组装与 JSON 解析 |
| 选路 | `ContentSource` | 有模型走模型，失败/超时/返回空一律退回样本 |

**关键决定：生成发生在"排期之后、兑现之前"，不是发布那一刻。**

发帖时 `InteractionPlanner`（纯逻辑、不联网）照旧用预置台词把内容填好并落库，
发布流程**不等模型**；落库之后 `unawaited(scheduler.upgradeCommentsWithModel(postId))`
才在后台把还没兑现的那些换成模型写的。这么排的好处：发帖不卡（写五条评论要好几秒）、
排期里永远有兜底内容（模型挂了社区照样有人说话）、已经兑现的不动（评论不在用户眼皮底下变）。

**一次请求写整批，不逐条调用**：一次发帖五到八条评论，逐条就是五到八次往返；而且同一批
一起写出来的能互相避开同一句话——"这张天空照真好看"被三个人说，一眼就是假的。

**模型写的东西也要过本地词表**：住民里有"毒舌调侃型"，让它自由发挥有风险；命中就把
那一条丢回预置台词。这里**不调模型审核**（那等于每条评论花两次钱）。

**砍掉设置开关的后果**：用户不必选"用样本还是用模型"，配了模型就是它在写。

**踩到的坑**：`insertPlanned` 的排期 id 是「帖子 + 序号」，所以同一条帖子只能排一次期——
写测试时一天里给同一条帖子排了两次，主键直接撞上了。产品代码里没有这个问题
（发帖只排一次），加注释记下了。

**基线**：175 个测试全过（新增 24 个）、`flutter analyze` 零问题。

**仍然敞着的**：

1. `upgradeCommentsWithModel` 是 fire-and-forget，切到清醒模式也拦不住它，会白花一次调用
2. 生成的评论只过本地词表，没走模型审核

### B3 · 住民的世界（2026-09-19 完成）

**这是那条分界线**：从这一版起，住民不再只在你的帖子底下出现。

| 做了什么 | 在哪儿 |
|---|---|
| 住民自己发动态（内容） | `ContentGenerator.residentPosts`：样本按**圈层模板 + 作息**拼，模型一次写整批 |
| 世界的钟 | `WorldService.tick()`：冷启动 + 心跳的 30 秒档各查一次 |
| 住民之间互相串门 | `_schedulePeers`：每条动态排 0—2 条邻居的评论 |
| 住民主页 | `/resident/:id`：资料、作息、他发过的动态 |
| 入口 | 信息流卡片、帖子详情、评论区的头像与名字都能点开 |
| 通知的分寸 | 兑现时先查帖主——**住民动态底下的互动不通知用户** |

**关键决定：动态"发生"在过去，而不是"刚刚"。**

tick 不是"现在生成一条，时间戳打现在"，而是先把 `[上次水位, 现在]` 这一段切开，
再让每个人落在其中一个时刻上。所以隔了一夜打开 APP，看到的是一夜之间陆续发生的
事，而不是一屏时间戳相同的"刚刚"。水位存在 `app_settings.world.lastTickAt`，
首次运行时只记不生成——空信息流是新用户的真实起点（阶段 A 定的），一进门就冒出
五条别人的动态会把这个起点冲掉。

**一次最多补四条**。走了再久也不一口气灌进来：那不是"社区热闹"，那是刷屏。

**住民动态的评论用样本，不走模型**：动态本身已经是一次模型调用了，底下的串门
是配角，不值得再花一次钱。

**踩到的坑（一个真 bug，而且是阶段 A 埋下的）**：
`PostRepository` 的 id 生成写着"时间戳 + 随机后缀"，但那个"随机"其实是
`时间戳.remainder(max)`——**拿时间戳当随机数**。用户手动发帖一次只插一条，撞不上；
世界 tick 一次要连着写好几条，同一毫秒内时间戳相同、后缀也相同，主键当场冲突。
已改成 `dart:math` 的 `Random`。

**基线**：190 个测试全过（新增 15 个）、`flutter analyze` 零问题。

**仍然敞着的**：

1. 住民主页还没有"你和他关系到哪一步了"——那要等 B4 的关系表有数据
2. 住民动态只有文字（图片素材还没有）
3. 住民之间的 @、转发、互相关注还没做

### B3.5 · 住民的形象（2026-09-19 定，B3 的续篇）

> **起因**：住民有了自己的生活（B3），接下来该有"自己的样子"。
> 这一节是 B3 之后提的想法：让住民能用文生图模型换头像、发图文帖、
> 顺带改自己的签名。
>
> **文生视频明确不做**：贵一个量级、慢到分钟级，而且普通学生发视频的频率
> 本来就低——做了反而假。

**按"表达渠道的重量"分层，先轻后重**：

| 层次 | 成本 | 风险 | 顺序 |
|---|---|---|---|
| 改**签名**（bio / 状态） | 极低（纯文本） | 无 | ① |
| 改**头像** | 高（一次文生图） | 中（用户认不出人） | ② |
| **图文帖** | 高 | 中 | ② 同批 |
| 改**昵称** | 极低 | **高** | ③ 最后，且必须留痕 |

签名先做，因为它是人最常用来表达心情的地方（QQ 状态、微信签名），
零成本，立刻有味道。头像最有效果但也最危险——**住民一旦频繁换脸，
社区"这些人一直在"的根基就松了**。

**关键决定**：

1. **模型配置分用途**（chat / image），允许只配其中之一。
   文生图和聊天通常不是同一家、同一个模型，硬要用一条配置是强人所难。
2. **换头像必须有理由**，不随机。真人换头像的时机就那么几种：
   心情转折（低落时换成暗的）、和你的关系走到某一步（要等 B4）、
   校园事件（要等 B6）。随机换头像 = "程序在动"。
3. **一个 tick 最多一张图**，再加概率打折，一天下来 1—2 张。
   图像生成比文本贵一个量级。
4. **图必须"像手机随手拍的"**：构图上乘、光影完美的 AI 图会立刻露馅，
   真人发的都是模糊的、歪的、带噪点的。prompt 里要死死压住这条，
   甚至主动加轻微模糊。
5. **人物一致性不用操心**：住民发的是"他看到的东西"（风景、食物、座位），
   不是自拍，所以不存在"同一个住民的图里人长得不一样"的问题。
6. **生成的图也过审核**：prompt 是我们自己写的、跑偏概率低，
   但配了多模态模型时仍然审一次。

**图文帖的触发（按"值不值得拍"筛）**：

- routine 里有值得拍的场景：操场、食堂、湖边、图书馆靠窗。
  宿舍睡觉不值得拍——按 place 白名单筛，或者给 `persona_routines` 加标记
- 私信里的"给你看看"（B5 之后最自然，因为本来就是一问一答）
- 换头像时顺手发一条："换了个新头像，最近心情不错"

**技术上的两块底座**（这一节的主要工作量）：

- `model_configs` 加用途列；`ModelGateway` 多一条生成图片的通道
- 住民从"只读的内容资产"变成"有当前状态"：`ai_personas` 表里那份是
  当前值，`assets/personas.json` 里那份退回成出厂值。住民改过签名或头像之后，
  读的时候以表为准

**进度（2026-09-30）：第①层「改签名」与「图文帖」都做完了，只剩头像。**

- **两层底座先落地**。`PersonaStateRepository` 把"出厂值 + 当前值"合成一份：
  `assets/personas/personas.json` 回答"他本来是谁"，`ai_personas` 表回答
  "他现在是什么样"，全 App 的住民资料（信息流作者名、评论、住民主页）
  统一走它。住民写了新签名的**只写表**，出厂那一份不动——新装用户永远
  该有一份完整的初始社区，而且住民把自己改得离出厂设定很远之后，
  还需要一个地方对得上"他本来是那样的"。
- **签名跟着动态走，不另开定时任务**。改签名的由头就是他刚发的那条动态，
  而那条动态正是这一次 tick 生出来的。内容层（模型或预置句）跟动态**同一次
  生成**里给一句签名，`ResidentSignature` 只管"轮到谁"：同一人 3 天冷却、
  一次 tick 最多一个、冷却过了还有 0.3 的概率打折。两层缺一不可——
  只有冷却的话，用户一天开五次 APP，社区看起来就像"这帮人天天在换签名"。
- **写成小作文的不算签名**（超过 20 字直接作废，不截断），**没过本地词表的
  也不换**——签名挂在主页最显眼的地方。
- **冷却水位存在 `app_settings`**（`resident.bio.lastAt.<住民 id>`），
  和 `world.lastTickAt` 一个性质：它是调度水位，不必为它在住民表上加一列。
**图文帖（同一天的第二件）**：住民会给自己的动态配一张自己拍的照片。

- **图是后补的，不跟发帖一起等**。出图要几十秒，而发帖那条路在冷启动里跑着，
  等它一下，用户开机就得先看几十秒空白。所以顺序反过来——文字先发出去，图生成
  好了再挂到那条动态上；生成失败就停在纯文字，**那条动态本身照样成立**，
  水位也不记（没成的事不该占掉下一次的机会）。
- **"值不值得拍"用排除法**：宿舍（睡觉）、广播站（值班）、后勤楼（办事窗口）
  不值得掏手机。判据是**精确匹配**——`宿舍楼下` 是另一回事（外卖、等人、
  傍晚的灯），不该被 `宿舍` 两个字一起扫掉。作息对不上的住民**不排除**：
  没登记几点在哪，不等于没什么可拍的，这时按圈层给一个画面
  （运动→操场跑道、摄影→傍晚的天空……），省得所有图长成同一个样子。
- **提示词压的是"太好看"**：构图讲究、光影完美的图一眼就是生成的，而真人随手拍
  的是歪的、有点糊、带噪点的。所以除了交代场景与时刻，还要**主动要那些缺点**。
- **频率跟签名一样克制**：全局 8 小时冷却 + 0.35 概率 + 一次 tick 最多一张，
  一天下来 1—2 张（图比文字贵一个量级，也慢一个量级）。
- **图片审核这次没做**（"仍然敞着的口子"第 1 条还是它）：要审图得先有多模态
  通道，而用户配的聊天模型多半不带视觉，做了也是常年落在"审核失败即放行"上，
  看着有、其实没用。等能配视觉模型了再说。

**剩下的头像**：按原计划要等一个"说得出口的理由"——B4 的关系推进、B6 的校园
事件都能当由头，随机换脸会把这个社区"这些人一直在"的根基抽掉。

### B4 · 关系与记忆（2026-10-12 完成）

四件事分四层，彼此有依赖顺序：先有规则，才有账；有了账，说话才带得上它。

**① 关系推进规则**（`lib/domain/services/relationship_rules.dart`，纯逻辑）

- 事件权重：点赞 1 / 关注 2 / 评论 3 / 回复 4 / 私信 5。点赞是"路过看了一眼"，
  私信是"专门想跟你说句话"，在一段关系里的分量本来就不一样。
- 档位门槛（亲近度）：眼熟 3 / 互关 10 / 熟人 22 / 好友 40。一次评论就到眼熟，
  互关要约 4 次，好友得是大半个月一直有来有往。
- **同一个住民 6 小时内只长一次亲近度**：一天里被同一个人反复搭话，亲近感不会翻倍。
  互动次数照记（界面上那句"你们互动过 12 次"是真事），长的是关系，不是计数。
- **档位只升不降**：不做"太久没说话就退回陌生"——那是产品要不要做得那么刻薄的问题，
  真要做也该是一次显式清理，而不是让每一次互动都提心吊胆。
- `eventFrom()` 认不出的类型一律当点赞：宁可少涨一点，也不把关系推得比实际更近。

**② 关系仓储与两个挂点**（`relationship_repository.dart`）

- 表在 B1 就建好了，B4 是第一次真去读写它。**没打过交道的人不占行**——读不到就是陌生，
  不必为 32 个住民各插一行空记录。
- 挂点一：`SchedulerService.flushDue` 兑现互动时推进，但**只算"对你"的那些**。
  住民彼此之间的互动不记——他们互相点赞跟你没关系，也不该让你和谁变熟。
- 挂点二：`InteractionRepository.addMyComment`——**你主动接住民的话**也算一次。
  只等着别人来找你，熟不起来。
- 两处都整段包 catch：关系是我们自己的一本账，它没记上不该让"有人评论了你"
  这条通知消失，也不该让你刚打的那句话发不出去。

**③ 记忆摘要**（`memory_summarizer.dart`）

- 存在 `ai_relationships.memory_summary`：**一句话，不是聊天记录**（决策 5）。
  素材是你最近 5 条帖子（`PostRepository.recentMine`，只要你自己发的），
  产出是每个人自己那句——摄影的人记住那张天空照，爱学习的人记住图书馆。
- **一次请求写完整批**（和评论一样）：八个人分别问一遍模型，既是八次花销，
  也容易让八条记忆长得一模一样。
- 触发时机：兑现互动之后**异步**（`unawaited`），只给这次打过照面的那几个人；
  12 小时冷却（水位放 `app_settings`，与世界 tick 一个性质）。
- **兜底是"截一句原话"**（`localGist`）：没配模型、模型挂了、或者它一条都没写出来时，
  从最近那条帖子里截第一句。它不如模型写得好，但"记得你发过什么"这件事是真的。
- 失败不影响主流程：整段包 catch，最坏的结果是"记忆还是上一次那句"。

**④ 喂进提示词，并影响频率**

- 评论提示词多一行 `你和他的关系：熟人｜他记得：他上次拍过一张天空照`。
  **陌生人不写这一行**——"不熟"本来就是这个社区默认的样子，写出来只是让模型分心；
  记忆那半截还看住民自己的 `memoryEnabled` 开关。
- 样本层没法自然"提起你上次那张天空照"，能做的是另一件事：**熟人话多一点**——
  同一个住民写了好几句台词时，已经互关的从长的那批里挑。
- 排期（`InteractionPlanner.plan(relations:)`）：关系 ≥2 的人抽签时**多拿一张票**，
  ≥4 再多一张；评论概率每档 +5%，上限 0.95。
  刻意不是"熟人必定到场"——每次都在那是订阅了通知，不是朋友。
  传空表（还没有关系数据）时行为与 B4 之前**完全一致**。

**关于"几天后的追问"**：这一条不另做机制，靠上面两件事自然长出来——熟人更常出现在
你的新帖下面，而他开口时**带着上一次记住的事**。真正"有上下文的追问"（楼中楼）
按决策 4 留在 B7，B4 不提前做。

**看得见它**：住民主页多了一张「你和他的关系」卡（档位 + 互动次数 + 他记得的那句）。
关系推进与记忆本来都发生在后台，这是它们唯一露头的地方——没有它，用户只会觉得
"他说话好像熟了一点"，却说不清为什么。

**基线**：304 个测试全过（B4 新增 40 个）、`flutter analyze` 零问题、schema 仍 v12（不需要迁移）。

### B5 · 私信与消息页（2026-10-12 完成）

**① 私信是"一段对话"，不是另一条评论区**（`private_message_repository.dart`）

- 表在 B1 就建好了（`private_messages`），这一版是第一次真去读写它。
- **时间戳当调度**：住民回你那句话先写好、`created_at` 落在几分钟之后，
  读的时候按 `created_at <= 现在` 过滤——所以你会觉得"他过一会儿才回"。
  这比另开一张待发队列省事，也顺带解决了补发：进程被杀掉，那条消息照样躺在
  库里，下次打开就到了。**没有加表、没有迁移**（schema 仍 v12）。
- 会话列表一条 SQL：每个聊过的人取最后一条 + 数一数没读的；
  表情包与语音在列表上显示成「[表情包]」「[语音]」，不铺路径出来。

**② 什么时候会有私信**（`direct_message_service.dart`，挂在冷启动与心跳上）

- **他主动来找你**：关系到互关以上的人才会来敲门（**完全靠 B4 的关系数据**），
  而且要过 20 小时的门槛——一开 APP 收到一串"在吗"，那就不像人了。
- **接你一句**：你发完话，他 40 秒—8 分钟之后回。你说完可以先干别的。
- 一次 tick 最多处理 3 个"欠着回话"的会话；清醒模式里什么都不做。

**③ 口吻分成三套**（`ContentGenerator` 的第三个方法）

- 评论是当着一屋子人说的，动态是自己起头，私信是关起门来跟一个人说。
  所以 `comments` / `residentPosts` / `directMessages` 各一个方法，谁也不借谁的词，
  样本台词也各写各的（`directOpeners` / `directReplies`）。
- 有上文的要接住上文（给模型最近 6 条往来），没上文的就是他先开口。
- **没有"对方正在输入…"**（规划书 §3.5 明确删掉了它）——这里的节奏是故意的：
  你发一句，他过几分钟才回。

**④ 界面**：底部导航加「消息」（回响模式 5 个 tab，对齐规划书 §5.1）、
会话列表、聊天页（气泡 + 表情包 + 输入栏）、未读红点。
聊天页每 20 秒自己重问一次——不然那句"过一会儿才回"的话，要等你退出去再进来才看得见。

**⑤ 关注**：关系走到互关档时**他会关注你**（`RelationshipRules.followAfter`），
不是随机某天忽然关注——一个从没跟你说过话的人突然关注了你，最像机器人。
住民主页有「关注 / 回关 / 互相关注」按钮。

**两个有意的取舍**：

- **私信不产生通知条目**，红点挂在底部导航和会话列表上。通知说"有人给你发了私信"、
  点进去却还看不见（因为时间戳还没到），比没有通知更糟。
- **独立的关注 / 粉丝列表页没做**——它属于"看数据"这一类，和 B9 一起更合适。

**这一轮补上的**：关注 / 粉丝列表页（消息页右上角进去），两个方向分开放。
**剩下的**：私信里的语音（等 B8 的 TTS）。

**基线**：348 个测试全过、`flutter analyze` 零问题、schema 仍 v12。

### B6 · 话题、热榜与时间感（2026-10-12 完成）

**已完成的三块**：

- **热榜算法**（`domain/services/trending.dart`，纯函数 + 15 个用例）：点赞 1 分、
  评论 3 分（说话比点赞重），**半衰期 12 小时**——昨天的爆款不该永远压着今天的新帖；
  时间戳在未来的（排期帖）不衰减。并列时新的靠前；话题并列按帖子数、
  再并列按名字定序（**定序是为了"两次查询结果一样"，不是因为它有意义**）。
- **校园事件**（`domain/services/campus_calendar.dart`）：节日 / 考试周 / 开学 /
  降温 / 高温，**按公历粗略切**（不查农历、不接天气服务——这是作品里的校园，
  不是气象台）。它同时喂两处：模型提示词里的"最近大家身边"，和样本台词
  （降温那天半个社区喊冷）。**顺序就是轻重**，节日排最前。
- **社区时间感**：世界 tick 挑人时**优先挑这个点本来就活跃的人**——
  凌晨三点发"又要起床上班"的住民，一眼就是排期器写的。
  （`WorldService.planMoments` 里那句注释本来就写着这个意图，这一版才真的做到。）
- **热榜页**（`features/trending/`）：最近大家身边 + 今日热帖 + 热门话题 +
  这两天话最多的人；入口在首页标题右边那团火。

**这一轮补上的**（2026-10-12）：

- **话题页与话题详情**：话题按热度排（复用 `Trending.rankTopics`，所以它和热榜页上
  那一块永远是同一个答案），点进去是该话题下的帖子。
- **信息流收敛成两栏**（推荐 / 关注），而不是五个标签堆一排：热榜、话题各自成页，
  搜索独立入口。**"同校"跟着世界观一起去掉了。** 关注栏是"我关注的住民 + 我自己"
  （不带上自己，刚发完帖切过来会以为丢了）。
- **搜索**：搜住民（名字、简介、圈子）和帖子（正文、话题）。逻辑是纯函数
  （`CommunitySearch`，有单测）；搜的只有本机这些数据——没有"全网搜索"。

**还没做的**：把"大家身边的事"做成事件的**独立流**（现在只是热榜顶上那条提示）。

### B7 · 楼中楼追问（2026-10-12 完成）

**① 平的 → 能读的**（`domain/services/comment_thread.dart`，纯函数 + 6 个用例）

- 数据库里评论是平铺的（`parent_id` 指一下），一屏评论要读得下去，就得让回复
  跟在自己回的那条后面、缩进一层。
- **最多两层**：手机屏幕上三楼就开始读不动了。太深的挂到还装得下的那一层，
  而不是丢掉、也不是浮到最外面。
- **一条都不能消失**：父评论被删了、没加载到、甚至数据绕成环（A 回 B、B 又回 A），
  一律当顶层——一条看不见的评论，比一条位置不完美的评论糟糕得多。

**② 追问必须"有上文"**（`domain/services/comment_reply_service.dart`）

- 触发只有一种：**你在评论里回了某位住民**。没有"随机让谁找个帖子追问"这种排期——
  那正是阶段 A 明令禁止的（同一个人平白多出一条语气不同的评论，一眼就是假的）。
- 楼只到两层：他要是在回别人的回复了，就不再往下叠。
- 他隔 1—12 分钟回来。调用方**不 await**：你那条回复已经发出去了，
  社区少一句追问不算塌天。
- 队列那边多了一个 `insertFollowUp`：与发帖的批量排期分开，因为 id 的来路不同——
  批量排期用 `sched_<帖子>_<序号>`，同一条帖子再排一次就会撞上。

**③ 口吻第四套**（`ContentGenerator.replies`）

- 不是评论（当着一屋子人）、不是动态（自己起头）、不是私信（关起门来），
  是**楼中楼里的一句**：上文只有两条，而对方就站在那儿等着。
- 提示词里把"你说过什么、他回你什么"原样给出来：楼中楼最容易演砸的地方，
  是答非所问——上一句说得很具体，下一句却像在自言自语。

**④ 界面**：缩进 + 左侧一条细线（`CommentTile.isReply`），一眼看得出它接的是哪句话。

**⑤ 住民之间也会追问**（这一轮补上）：他的动态下面有人评论了，他隔一阵回一句——
楼中楼里最常见的其实是这种对话，不是"用户和 AI"。规矩完全一样（**有上文才追**，
`parentId` 指着那条评论），只是频率压到四成：一屏评论条条有来有回，那像客服。

**基线**：368 个测试全过、`flutter analyze` 零问题、schema 仍 v12。

   但真机上要看效果得先配一条文生图模型（目前只配了 chat）。

### 一次世界观换代：去掉「学校」（2026-10-12）

**为什么**：要的是一个**自由社区**。带着学校背景，住民的身份、说话方式、圈子全被框住——
"二食堂测评员""失物招领小助手"这类 ID 只有校园里才成立，社区也就长不成真的社区。

| 位置 | 之前 | 之后 |
|---|---|---|
| 住民人设（32 人） | 校园社区里的学生 | 生活里的各种人：便利店店员、修电脑的、夜班护士、咖啡师、面馆老板、跑团组织者、电台主播、遛狗的、阳台种菜的、白天送外卖晚上打鼓的…… |
| 圈子（12 个） | 同校圈 / 学习 / 失物招领 / 表白墙 / 社团招新… | 日常 / 吐槽 / 职场 / 深夜 / 树洞 / 运动 / 摄影 / 美食 / 读书 / 音乐 / 宠物 / 出行 |
| 提示词 | 「回响大学」校园社区里的几名**学生** | 「回响」这个社区里的几名**普通人** |
| 日历 | `campus_calendar.dart`：开学、考试周、"校园里" | `community_calendar.dart`：节日、周末、降温高温——**只留"大家共同经历的事"，不设任何群体的日程** |
| 配图场景 | 宿舍 / 广播站 / 后勤楼不值得拍 | 家 / 床上 / 沙发 / 工位 / 会议室不值得拍 |
| 默认昵称 | 「同学」 | 「路人」 |

**顺带补上的机制：内容资产换代**（`SeedService`）

住民是**内容资产**，而播种一直是"只补不覆盖"——老库永远拿不到新内容，
这一版换了一整套人设，这个窟窿就藏不住了。

所以加了**内容版本号**（assets 的 `_schemaVersion`）：版本变了就整批刷新内容字段
（名字、人设、语气、圈子、作息），**运行期那本账一个字都不动**——和你的关系、
记忆、私信、互动、帖子都留着；他换过的签名会跟着内容一起换代（那本来就是出厂值）。
老库第一次升上来没有版本号，正好走这一趟。

老帖子的**话题标签**也跟着映射换代（`legacyTopics`）：帖子本身是历史不动，
但"同校圈"这种分类留在新社区里会一直出戏。

**基线**：371 个测试全过、`flutter analyze` 零问题、schema 仍 v12（不需要迁移）。

### 顺带补上的：用户也能说话了（2026-09-19）

实测时发现有件事一直缺着：**评论区底下那对"♡ 0"和"回复"是死的**——
从阶段 A 起就是纯装饰，只是个能点的样子。而信息流里点不动赞。

社区是单向的：住民在说话，用户只能看着。B3 之后住民的动态进了信息流，
这件事就遮不住了。

| 补的东西 | 落在哪儿 |
|---|---|
| 给帖子点赞 | `posts.liked_at`：一人一条帖子一颗心，直接记在帖子那一行上 |
| 给评论点赞 | 单独一张 `comment_likes`——评论有很多条，而且点的可能是住民的、也可能是我自己的 |
| 自己的评论 | 新表 `user_comments`，与 `ai_interactions` 分开 |
| 回复某一条 | `user_comments.parent_id` + `reply_to_name` |

**为什么用户的评论不塞进 `ai_interactions`**：那张表是"排期与兑现"的队列
（`scheduled_at` / `status` / 取消 / 补发），而"我刚回了句什么"没有这些事。
分开存，合并发生在读取那一层——一个 UNION 让数据库把两条来源排成一条时间线。

**迁移踩的坑（值得记）**：`user_comments` 是 v11 建的，`parent_id` 是 v12 加的；
但 Drift 的 `createTable` 用的永远是**当前**的表定义，所以从 v10 及更早升上来时，
v11 那一块建出来的表**已经带着** v12 才该有的列，v12 再 `addColumn` 就是
`duplicate column name`——老库和新装用户都会在启动时炸。
修法是让 v12 的那两句只在 `from >= 11` 时执行。

**这个坑是被迁移测试抓住的**（那是一个真的 v8 库一路升上来的测试）——
如果只测"新库能不能建起来"，它会一路绿到用户手机上。

**另外一个来由**：这一版最初在帖子详情页给点赞做了个带边框的胶囊按钮，
实测时被一句话点破——"为什么又新加了一个小卡片来显示点赞，冗余了"。
同一个动作在两处长得不一样，用户会以为是两件事。已改回与信息流一致的那颗心。

**基线**：217 个测试全过、`flutter analyze` 零问题。

**顺带补上的主题注脚**：住民"给自己生成头像"这件事，正好是戈夫曼那个
前台/后台的镜像——用户在精心挑选自己的网络形象，AI 住民在做一模一样的事，
甚至更彻底（连照片都是生成的）。规划书 §14 那张映射表里"戈夫曼前台/后台"
这一条，本来只有"发帖、修图"几个落点，住民换头像能把它补成闭环：
**你精心打造的形象，和 AI 随手生成的形象，本质上是同一件事**。

### B8 · 真实语音（2026-10-14 完成）

**离线合成 + 离线识别，模型随包走，一个字都不上传。**

阶段 A 的"语音条"是两个数据库列加一个静态气泡：波形是 `i % 5` 画出来的，
`voice_path` 指的那个 mp3 在仓库里根本不存在，住民身上那个 `voiceModel`
字段从头到尾没人读过。这一版把它接成了真的东西。

**运行时**：`sherpa_onnx`（Dart FFI 绑定，Apache-2.0）。一套库同时管合成与识别，
Android / Windows 都能跑。模型打进 APK（合成 31 MB + 识别 78 MB），
但**不进 git 仓库**——`assets/models/*/_placeholder.txt` 里写着下载地址，
许可证也一并核过（AISHELL-3 与 Paraformer 的模型卡都是 Apache-2.0）。

**合成**（`tts_service.dart` + `voice_waveform.dart`）：

- 模型 `vits-icefall-zh-aishell3`：一套模型带 174 个说话人，30 MB
- **音色是写死的表**（`resident_voice.dart`）：32 位住民各占一个编号，
  按语气标签分男女池后顺序取（`female` 判定要放在 `male` 前面——
  `voice_soft_female` 里也含 "male" 四个字母，写反了一半女声会变男声）。
  表外的新住民按 id 稳定散列兜底。音色一旦会漂，"社区里住着固定的人"这件事就没了
- 语速也来自语气标签：`lazy` / `quiet` 慢 6%，`bright` / `loud` 快 6%
- 合成完立刻写 wav 进 `media/` 目录，返回 `file:` 引用；
  **时长按采样点数算、波形按峰值抽 22 根**（替换掉那 22 根假竖条）
- 波形**不存库**：它是音频的一个视图，读文件算一遍即可 —— 因此这版**没有数据库迁移**

**识别**（`asr_service.dart` + `voice_recorder.dart`）：

- `sherpa-onnx-paraformer-zh-small`（int8，78 MB）
- 录 16 kHz 单声道 wav（录音器直接录成模型要的格式，省一次重采样），
  松手转成文字、**只填进输入框**，用户还能接着改
- 隐私上说得直白一点：识别在本机做，录音不离开设备

**两个关键决定**：

1. **语音评论是"后补"的，不是一开始就标成语音**。兑现时先按文字落库，
   合成成功再用 `attachVoice` 升级成语音条（与 B3.5 的图同一个套路）。
   反过来做的话，评论区会先出现一排点不响的播放键 —— 那比"文字变成语音"更假。
   合成失败就停在文字：语音是表现形式，不该连累内容。
2. **一条帖子最多两条语音**（`InteractionPlanner.maxVoicesPerPost`），
   概率跟着语气标签走（懒得打字的 0.34、一般 0.16）。评论区一半人在发语音，
   那不是社区，是语音信箱。

**Windows 上踩的坑**：`System32\onnxruntime.dll` 是系统自带组件在用的旧版本
（ORT 1.17），sherpa 的原生库依赖同名文件，隐式解析先撞上它 →
`requested API version [28] is not available` → 整个进程崩掉。
解法是在加载 sherpa 之前，先把**包里那份**按绝对路径加载进内存
（`speech_runtime.dart`）：同名模块已经在内存里，后面解析依赖就复用它。

**包体积（实测）**：带全部 ABI 的 release 包 **235 MB** ——原生库
（ONNX Runtime 是大头）136 MB + 模型 98 MB。真机是 arm64，
`flutter build apk --release --split-per-abi` 出来的那个 **146 MB**，
省下 89 MB。两个坑记一笔：

- `--target-platform android-arm64` **不够用**：它只管住 Flutter 自己的
  `libflutter.so` / `libapp.so`，插件自带的 `.so`（onnxruntime、sherpa）
  照样三个 ABI 全进，实测只小到 194 MB。要真瘦身得按 ABI 拆包
- 模型那 110 MB 是功能本身，砍不掉（除非改成首次启动下载，
  但那会让"飞行模式下也能听"这条验收变得依赖网络）

两条都写进 README 的打包段了。

**基线**：393 个测试全过、`flutter analyze` 零问题。
语音相关 16 个用例（`test/voice_test.dart`）：音色固定性与男女池、波形归一化、
wav 解析、语音条的渲染（含合规小字那一条），以及
"兑现 → 合成 → 升级成语音条"这条接线（用假合成服务，不碰真模型）。

**仍然敞着的口子**：

1. **私信还是纯文字**（`private_messages` 有 `voice_path` 列，但没接）——
   第二幕"深夜私信"那条线本来最该有声音
2. 语音条**不能拖动进度**，也没有播放进度高亮
3. 合成跑在主 isolate：一段 20 字的话在桌面约 100—200 ms，手机上更长，
   卡的那一下是能感觉到的。真嫌卡再挪进 isolate
4. 合成出来的采样率是 **8 kHz**（模型自身如此），听感偏电话音。
   想要更厚的声音得换模型（fanchen-C 114 MB / kokoro-int8 140 MB），
   代价是体积
5. 174 个说话人嗓门大小不一，没做音量归一化：同为"女声"，有的条子明显偏轻

### B9 · 数据看板（2026-10-14 完成）

**两种模式看的是两个世界，不是同一页的两个皮肤。**

规划书里这个功能的落点很明确（§3.10 / §4 / §6.9）：回响模式要给用户看清
"这些动静是 AI 造出来的"，清醒模式则只给真实记录、一条虚拟数据都不掺。
把两者混在一页里显示的话，看板自己就成了那个把人绕进去的东西——
用户会分不清哪些数字是"有人真的喜欢我"。

**做了什么**

- `lib/features/dashboard/dashboard_page.dart`：一个入口，两套内容
  - 回响侧：四个数字（今天发帖 / 收到的赞 / 收到的评论 / 关注我的人）、
    最近 7 天点赞与评论的双线趋势、14 天的 24 小时互动高峰、
    以及"最近半小时查看反馈 N 次""本周亮屏等待 N 次"
  - 清醒侧：本周记录数、真实行动数、我重视的事、连续记录天数，外加一句
    "为什么这里看不到点赞"
- `lib/domain/services/dashboard_stats.dart`：按自然日分桶、24 小时分布、
  高峰钟点、环比。**纯函数**
- `lib/data/repositories/dashboard_repository.dart`：只往外拿原始的点
  （帖子时刻、已兑现互动的时刻与类型、关注人数、收到的私信数）
- 设置页「清醒模式」分组下加「数据看板」入口（两种模式都能进）

**四个决定**

1. **聚合放在 Dart 里，不放在 SQL 里**。SQL 里算错一个 `GROUP BY`，
   页面上是一条看着挺像回事的假曲线，而且没人看得出来。现在原始点出来、
   纯函数分桶——那组函数全都有测试。
2. **图表自己画**（`CustomPainter`）。折线一张、24 小时柱状一张，
   为这个引一个图表库不划算；而且第三方库的默认样式一眼就是"模板感"。
3. **只看已经发生的**：`ai_interactions` 里 pending 的排期不算，
   将来的点赞不该出现在"过去 7 天"里。
4. **"亮屏等待"是一个新指标**（`screen_wait`）：帖子详情页停留满 8 秒、
   而这期间评论区一条新的都没有 → 记一次。它和"查看反馈次数"是一对：
   一个是**动作**（我又点进来看了），一个是**动作的结果**（什么都没等到）。
   微电影第二幕里主角盯着屏幕那几秒，指的就是它。**只记一次，不弹窗、不打断**——
   这件事的价值在于用户以后在看板上自己看见它，而不是在被记录的那一刻被说教。

**基线**：403 个测试全过、`flutter analyze` 零问题。
看板相关 9 个用例（`test/dashboard_test.dart`）：分桶窗口、匿名人群批次按人计、
高峰钟点、环比（前半段为 0 时不说百分比）、两种模式各自的数据源、
以及"回响看板上那句 AI 标注必须在"。

**仍然敞着的口子**：

1. 看板的时间范围写死（趋势 7 天、高峰 14 天），没有切换
2. 规划书 §3.10 提的"**实时**点赞增长曲线"没做——现在是打开页面时算一次，
   不会自己往上跳
3. "热力图"简化成了 24 小时柱状图：一屏的互动量还撑不起一张热力图
4. 清醒侧没有情绪维度（规划书 §4 的每周反思报告要它，留给 B11）
5. 未成年人保护那道年龄门还没做（B11）

### B10 · 系统级后台调度（2026-10-14 完成）

**先补了一个更基础的洞：系统通知从来没接过。**

`flutter_local_notifications` 在阶段 A 就写进了 `pubspec.yaml`，但全项目
**零引用**——所谓"通知"一直是应用内那张列表加一个红点，只在用户自己
打开 APP 时看得见。于是有个说不通的场景：帖子发出去、APP 划掉、
两小时后住民来评论了，用户什么都不知道，直到他下次主动打开。

这一版接上了真实的通知栏，再让 WorkManager 在 APP 完全关闭时按周期
把它叫醒一次。

**系统通知**（`lib/domain/services/notification_service.dart`）

- 渠道 `echo_interactions`，Android 13+ 走运行时权限（拒绝了照常跑，
  提醒留在应用内）
- **锁屏不露内容**：`NotificationVisibility.secret`——公共场合手机亮起来，
  "老陈的键盘 评论了你的帖子"不该被旁边的人读到；要看的细节解锁再看
- 通知 id **由互动 id 派生**：同一条互动重复补发只会覆盖，不会刷屏

**什么时候弹，什么时候不弹**

这里有个容易做错的地方：前台运行时也弹系统通知的话，用户正看着屏幕，
突然被自己的手机提示"有人评论了你"——那是打扰，不是提醒。
所以给调度器接的是一个**可空的回调**，只有后台那条路才注入它：

| 场景 | 应用内通知 | 系统通知 |
|---|---|---|
| 用户开着 APP，心跳补发 | 写 | **不弹**（红点已经够了） |
| APP 被杀，WorkManager 补发 | 写 | **弹** |
| 住民之间互相评论（不是回应你） | 不写 | 不弹 |

私信**不推系统通知**，沿用 B5 的决策（"通知说'有人私信你'，点进去却看不见
更糟"）。真机试过之后如果觉得该推，再单独议。

**WorkManager**（`lib/domain/services/background_worker.dart`）

- 周期 15 分钟——这是 Android 划的**最小**周期，不是我们的选择
- 回调用 `@pragma('vm:entry-point')` 标了：后台 isolate 从这里起跑，
  没有这个注解，编译优化会把它当"没人调用"删掉
- 后台 isolate 里没有 `ref` 也没有 widget 树，所以
  `runHeadlessTick()` 自己建一个 `ProviderContainer`（`inBackgroundTaskProvider`
  打开 = 这次要推通知），跑完就 dispose
- 不做播种：首次启动不会发生在后台
- 约束设成"不需要网络"：排期本来就在磁盘上，断网时来的评论照样该提醒
- **永远返回 true**：返回 false 会让系统按退避策略把任务越推越远，
  而我们要的是它照常来

**三条老路一条都没撤**：冷启动补发（`appBootstrapProvider`）、
回前台（`app.dart` 生命周期）、开着 APP 时的 30 秒心跳。
**验收标准是"补得回来"，不是"一定准时"**——Android 的省电策略随时可能
把周期任务推迟或合并，把可靠性押在它身上是不理智的，这里只把它当成
"多一层机会"。

**基线**：407 个测试全过、`flutter analyze` 零问题。
新增 4 个用例（`test/background_test.dart`）：后台补发会推通知、
点赞人数写进标题、前台不推但应用内那条照写、住民之间互相评论不打扰用户。

**仍然敞着的口子**：

1. **点通知只打开 APP，不回落到那条帖子**——深链要路由能带 payload，
   做一半的跳转比不跳更让人困惑，所以先不做
2. WorkManager 真实行为**只能在真机上验**：桌面跑不出来，模拟器的省电
   策略也和真机不一样。这一条留给真机回归
3. 通知没有分组/摘要：一次补发来三条评论就是三条通知（好在 id 派生
   让同一条互动不会重复弹）
4. iOS 侧的 `BGTaskScheduler` 只是插件自动带的注册，没做 iOS 专属配置
   （项目目前只有 Android 真机）

### B11 · 收尾（2026-10-14）

**三件事：一道独立的年龄门、周报的情绪维度、状态同步。**

**未成年人保护**（`lib/features/safety/minor_page.dart`）

规划书里这条只有一句话——"未成年人默认禁用回响模式"——但它和别的开关
不是一类东西：**它是给监护人的，不是给用户的**。所以：

- 它是一个**长期锁**（`safety.minorProtection`），不是"切模式时那个勾选"
  的重复：勾选是一次性的自我声明，每次切换都要重来（适合临时借用手机这类场景）；
  这道门开着的时候，回响模式的**任何**入口都不通
- 拦截放在 `runModeSwitch` 里——所有切换入口都走那个函数（设置页、首页、
  脚本演示、演示模式），所以没有漏网的
- 开锁时的顺序是**先锁门、再切模式**：反过来的话，中间有几十毫秒
  门开着而人还在回响模式里
- 页面上不劝、不解释产品优势，只把两件事说清楚：为什么它对还在长的人
  不合适，以及这道门管到哪一步

**周报的情绪维度**（schema v13）

- 真实行动记录多一个**可选**的心情（踏实 / 开心 / 平静 / 有点累 / 低落）
- 选填，而且能点掉（再点一次同一个 = 不记了）。一旦变成必填，
  它很快就成为一件差事，然后没人再记
- 周报里是一条按比例分的横条 + 一行数字。没记过时不说"暂无数据"——
  那句话像在催人填表；这里只需要告诉用户那个选项在哪
- 迁移上老记录一律是空 = 没记。**不替用户补一个心情**：编出来的心情比没有更糟，
  那这张周报就没有一句是真的了

**状态同步**：README 的状态段更新（阶段 B 完成、世界观换代、包体积与拆包命令）。

**基线**：414 个测试全过、`flutter analyze` 零问题。这一版新增 4 个用例
（`test/minor_protection_test.dart`）和 3 个心情用例（`test/clear_journal_test.dart`）。

**顺带修的两个测试问题**（都不是产品代码的错，但都值得记一笔）：
